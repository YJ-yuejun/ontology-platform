## 一、业务背景与目标
### 1.1 现状与本意
我们的本体是**标品**（下文称 **main**）。交付时整体复制一份给客户，客户在自己的分支上继续做本体构建与迭代：
```
                    ┌── A 客户分支（复制出来，迭代 1 个月）
标品本体 main ──────┤
                    └── B 客户分支（复制出来，独立迭代）
```
迭代一段时间之后，需要回答两类问题：
1. **分支相对 main 改了什么？哪些改动值得回流到 main？**
2. **A 和 B 两个分支之间，谁的做法更好？有没有可以互相借鉴、或者直接进 main 的？**
目的只有一个：**把各客户分支上验证过的好经验沉淀回标品**，而不是让它们散落在各个客户分支里。同时要能判断哪些是**客户特有**、不该污染 main。
### 1.2 因此这两个智能体不是"看一眼差异"
它们的定位是**回流决策的支撑工具**：

| 环节 | 谁负责 |
|---|---|
| 分支上改得对不对、模型本身站不站得住 | **本体质检智能体** |
| 分支相对 main 改了什么、哪些值得回流、哪些冲突 | **本体对比智能体** |
| 最终决定哪些回 main | **人**（智能体只给建议与证据，不自动合并） |

## 二、两个智能体的分工
| | 本体对比智能体 | 本体质检智能体 |
|---|---|---|
| 回答的问题 | 分支相对 main 改了什么？哪些值得回流？哪些冲突？ | 这份模型本身是否站得住？ |
| 输入 | 一个基准本体（main）+ 1～N 个分支本体 | 一个本体（main 或任一分支）+ 检查范围 |
| 输出 | 差异清单 + **回流建议报告** | 质检报告 |
| 使用时机 | 回流评审前；分支迭代一个阶段后 | 每次改完模型后；提交回流前 |
| 结论来源 | 字段级确定性比较 | 确定性规则检查 |
| 模型（LLM）的角色 | 只解释已生成的差异与建议，不参与判定 | 只解释已生成的报告，不参与判定 |
**两者共同的一条铁律**：结论必须确定性可复现。模型只能解释，不能改写结论；默认不开启模型外发。

## 三、本体对比智能体
### 3.1 业务要求
#### 输入
| 输入项 | 说明 | 是否必需 |
|---|---|---|
| 基准本体 | 标品 main（也可以是某个分支，用于 A vs B） | 必需 |
| 对比本体 | 1～N 个分支本体（A 客户、B 客户…） | 必需，至少 1 个 |
| 对比范围 | 全部资源段，或指定资源段（如只看对象类型与关系） | 可选 |
| 关注点 | 例如"只看值得回流的改动" | 可选 |
> 分支与本体的对应关系由「复制本体」时记录的来源（`origin_ontology_id`）建立，用于识别"这是从 main 复制出来的第几代分支"。
#### 输出
**输出一：结构化差异清单**（机器可读）
每条差异包含：所属资源段、资源名、稳定标识、变更类型（新增 / 修改 / 删除）、差异字段、左右原值。
**输出二：回流建议报告**（人可读，核心交付物）
必须回答"接下来该做什么"，而不只是"有什么不同"。报告分四类结论：

| 分类 | 含义 | 例子 |
|---|---|---|
| **建议回流** | 提升了语义完整性或覆盖度，对其它客户普遍有价值 | 新增了"设备点检记录"对象与关系；补了属性业务定义；新增了校验规则 |
| **客户特有** | 只对该客户的业务成立，不应进 main | 客户自己的业务域命名、客户专有场景、客户内部系统名 |
| **冲突** | 多个分支对**同一资源**做了方向不一致的改动，需人工裁决 | A 把字段类型改成 decimal，B 改成 string |
| **无实质差异** | 仅格式、空值、序列化差异，无需处理 | `null` 与空字符串；字段顺序 |
**输出三：风险提示**
删除项、主键变更、数据类型收紧、关系端点变更等**破坏性改动**必须单独列出并标注影响面。
#### 使用流程
```
main（标品）
  └─ 复制 → A 客户分支 ─ 迭代 1 个月 ─┐
  └─ 复制 → B 客户分支 ─ 迭代 1 个月 ─┤
                                      ├─ 对比：A vs main → 回流建议报告
                                      ├─ 对比：B vs main → 回流建议报告
                                      └─ 对比：A vs B    → 互相借鉴 / 谁进 main
                                                    ↓
                                        人工评审 → 决定合并项 → 回流 main
```
### 3.2 智能体怎么工作
#### （1）配对：按业务稳定标识，不按资源 ID
复制分支时所有资源都会拿到**新的 UUID**，只有业务标识（`name` / `code`）保留。因此配对必须按业务稳定标识：

| 资源段 | 配对键 |
|---|---|
| 业务域、主题域 | `code` |
| 对象类型、接口、关系类型、业务规则、动作类型 | `name` |
| 8 类企业资源（数据源、治理资产、数据映射、规则与函数、系统能力、动作执行映射、权限策略、业务场景） | `code` |
**实测**：按 UUID 配对会把复制出来的分支报成"整本删除 + 整本重建"（70 个资源产生 62 条假差异）；按稳定标识配对，未改动的副本与原体对比为 **0 差异**。
#### （2）引用归一化：不做这一步，每条关系都会被判成"已修改"
资源之间的引用存的是 UUID，副本里同样变了。比较前必须把引用换成本体内部的稳定标识：

| 引用字段 | 归一化为 |
|---|---|
| `business_domain_id` / `subject_domain_id` | 对应业务域 / 主题域的 `code` |
| `interface_ids` | 接口的 `name` 列表 |
| `source_object_type_id` / `target_object_type_id` | 对象类型的 `name` |
| `properties[].shared_property_id` | 置空（运行时引用，跨本体无意义） |
#### （3）比较范围与保护
- 覆盖 **15 类资源**；其中 8 类按字段白名单比较，7 类按全字段比较。
- 一律排除：`id`、`ontology_id`、创建 / 更新时间与操作人、状态与建模状态、各类计数字段、`metadata` 容器。
- **密钥保护**：字段名含 `password` / `secret` / `api_key` / `access_token` / `private_key` 的一律不参与比较与输出。
#### （4）回流分类怎么判定
分类以**客观信号**为依据，不靠模型主观打分：

| 信号 | 倾向分类 |
|---|---|
| 新增对象 / 属性 / 关系 / 规则 / 映射 | 建议回流（补充了覆盖度） |
| 补全业务定义、补全质量规则、补全来源字段 | 建议回流（提升了完整性） |
| 改动集中在业务域命名、客户专有场景、客户系统名 | 客户特有 |
| 同一资源在两个分支上被改成不同值 | 冲突 |
| 差异字段两侧语义等价（`null` 与空串等） | 无实质差异 |
| 删除、主键变更、类型收紧、关系端点变更 | 破坏性改动 → 风险提示，单独列出 |
> 说明：**"值不值得回流"最终是业务判断**。智能体的职责是给出分类信号、排序与证据，把人工决策的成本降下来，而不是替人拍板。
#### （5）多分支交叉分析
当对比本体多于一个时，除了"每个分支 vs main"，还要给出**分支之间的交叉结论**：
- 某改动只有在 A 出现 → A 独有
- 某改动 A 与 B 都有且一致 → 高置信度的回流候选（两个客户都验证过）
- 某改动 A 与 B 都有但不一致 → 冲突，列出两种做法
- 某改动 main 有、A 与 B 都删了 → 可能是 main 的问题，需复核
### 3.3 报告要出什么（输出契约）
| 章节 | 必须包含 |
|---|---|
| 1. 概览 | 基准本体、对比本体（可多个）、各自来源分支、对比时间、对比口径 |
| 2. 总量 | 新增 / 修改 / 删除计数，并按资源段分布 |
| 3. 回流建议 | 四类分组的清单：建议回流 / 客户特有 / 冲突 / 无实质差异 |
| 4. 逐条证据 | 每条建议：资源名 + 稳定标识 + 差异字段 + 左右原值 + 分类理由 |
| 5. 风险提示 | 破坏性改动清单及影响面 |
| 6. 多分支交叉 | 分支之间的一致项、分歧项、独有项 |
| 7. 后续动作建议 | 建议优先处理哪些，哪些待定 |
### 3.4 验收标准（看报告里的什么）
| 编号 | 验收项 | 判定方式 |
|---|---|---|
| C1 | 未改动的分支与 main 对比，差异为 0 | 复制 main 后立即对比，断言差异总数为 0、且不出现"整本新增 + 整本删除" |
| C2 | 改动能定位到资源与字段 | 改一个属性后对比，断言报告出现该资源且指出具体字段 |
| C3 | 报告给出**回流建议**而非只列差异 | 断言每条差异都落入四类之一，且带分类理由 |
| C4 | 冲突能被识别 | 构造 A / B 对同一资源改成不同值，断言报告标记为冲突并列出两种做法 |
| C5 | 跨分支一致项被识别 | 构造 A / B 相同改动，断言报告将其列为高置信度回流候选 |
| C6 | 破坏性改动被单独提示 | 删除一个对象后对比，断言该差异出现在风险提示中 |
| C7 | 每条建议可追溯到证据 | 断言建议条目的资源、字段、左右原值均可核对 |
| C8 | 密钥字段不出现在任何输出 | 数据源含密码相关字段时，断言输出中不含该字段与取值 |
| C9 | 空值等语义等价差异不产生噪声 | 一侧 `null`、一侧空串，断言不产生差异，或归入"无实质差异" |
| C10 | 对话解读与报告一致 | 追问"哪些建议回流"，回答的数量与名称必须与报告一致 |

## 四、本体质检智能体
### 4.1 业务要求
#### 输入
| 输入项 | 说明 | 是否必需 |
|---|---|---|
| 本体 | main 或任一客户分支 | 必需 |
| 检查范围 | 全部维度，或指定若干维度 | 可选（缺省全部） |
#### 输出
**输出一：质检结论** —— 待修复 / 通过（含警告）/ 通过。
**输出二：质检报告** —— 检查项通过情况 + 问题清单（级别、资源、描述、修复方向）+ 报告时效（是否仍对应当前模型）。
#### 为什么需要它
分支上的迭代是"某个客户在某个场景下"做的，容易出现：对象没有主键、接口契约没实现完整、规则没有表达式、映射引用了不存在的资产。这些在**回流 main 之前必须先自检**，否则会把问题带进标品。
### 4.2 智能体怎么工作
#### （1）九个检查维度
| 维度 | 判定要点 |
|---|---|
| 对象主键与标题属性 | 有且只有一个主键；标题属性必须来自已定义属性 |
| 关系端点与状态一致 | 两端对象存在；关系为 Active 时端点也应可用 |
| 动作目标与参数 | 指向有效对象；改写类动作应有参数 |
| 业务规则目标与表达式 | 指向有效对象且必须有表达式 |
| 接口实现完整 | 对象正确实现接口的属性契约（属性存在且类型一致） |
| 业务域与主题域分类 | 对象类型必须归入主题域 |
| 模型至少包含一个业务对象类型 | 本体不能为空 |
| 数据映射引用完整 | 映射引用的治理资产、对象与属性必须存在 |
| 规则与函数依赖完整 | 规则与函数的引用与实现配置必须完整 |
#### （2）范围裁剪：检查项与问题必须同时裁剪
传了范围之后，**检查项和问题清单要一起被裁剪到所选维度**。否则会出现"报告写着某项未通过，但那一项其实没查"的自相矛盾。
#### （3）模型指纹与时效（关键设计）
这是让报告能被当作**证据**使用的前提：
1. 把本体的语义索引按固定顺序序列化后取 SHA-256，得到**模型指纹**；
2. 质检时把指纹与报告一起存档；
3. 读取报告时重算当前指纹，不一致即标记为**过期**；
4. 过期的报告明确提示"不是当前状态的结论"，**不参与回流或发布判断**。
含义：**改一个描述文字也会让报告过期**。这是刻意的——报告必须能追溯到它检查的那个确切状态。
### 4.3 报告要出什么（输出契约）
| 章节 | 必须包含 |
|---|---|
| 1. 结论与摘要 | 结论 + "N/M 项检查通过；X 项错误，Y 项警告" |
| 2. 检查范围 | 本次检查了哪些维度（与检查项、问题清单严格一致） |
| 3. 检查项 | 每项的通过 / 未通过 |
| 4. 问题清单 | 级别（错误 / 警告）+ 资源类型 + 资源定位 + 问题描述 + 修复方向 |
| 5. 时效 | 模型指纹、生成时间、执行人、是否已过期 |
### 4.4 验收标准（看报告里的什么）
| 编号 | 验收项 | 判定方式 |
|---|---|---|
| Q1 | 全部维度质检产出九项检查 | 不传范围运行，断言检查项覆盖九个维度 |
| Q2 | 范围裁剪同时作用于检查项与问题 | 只传两个维度，断言两者均被裁剪且互相一致 |
| Q3 | 结论口径正确 | 构造仅含警告的模型断言"通过（含警告）"；构造错误断言"待修复" |
| Q4 | 摘要数字与问题集合一致 | 断言摘要中的错误 / 警告数与问题清单统计相同 |
| Q5 | 模型变化后报告过期 | 质检后改任一语义字段，断言报告被标记为过期 |
| Q6 | 过期报告不参与判断 | 构造过期报告，断言不返回可用结论 |
| Q7 | 报告可持久化与回看 | 连续质检两次，断言历史均保留且各自指纹不同 |
| Q8 | 问题能定位到资源 | 断言每条问题都带资源类型与资源标识，可跳转核对 |
| Q9 | 对话解读不改变结论 | 追问多个问题，断言结论与问题清单不变 |
| Q10 | 检查范围与后端维度定义一致 | 断言可选维度与后端定义一一对应 |

## 五、两个智能体如何协同（回流闭环）
```
① 客户分支迭代模型
        ↓
② 本体质检智能体自检 ── 不通过 → 分支侧先修
        ↓ 通过
③ 本体对比智能体：分支 vs main（必要时 A vs B）
        ↓
④ 回流建议报告：建议回流 / 客户特有 / 冲突 / 无实质差异 + 风险提示
        ↓
⑤ 人工评审决策（智能体不自动合并）
        ↓
⑥ 回流 main → main 再次质检 → 形成新的标品基线
```
**协同要点**
- 质检解决"这份模型本身站不站得住"，对比解决"改了什么、值不值得回流"，两者不可互相替代。
- 只有**质检通过且报告未过期**的分支，才进入回流评审。
- 回流到 main 之后，main 需要重新质检并形成新的基线；此后新复制出去的分支以新 main 为起点。
- 整个过程**只读**：两个智能体都不写回任何本体，合并由人执行。

## 六、给研发的定调（边界）
### 要做
1. 对比要支撑 **main vs 分支** 与 **分支 vs 分支** 两种用法，且能同时对比多个分支。
2. 对比的输出必须是**回流建议报告**，不是一份差异流水账。
3. 质检的输出必须能当**证据**用：结论可复现、范围自洽、带指纹与时效。
4. 两个智能体的对话只做**解释**，不得改变报告中的结论、计数与清单。
### 不做
1. 不做自动合并、不自动改写本体。
2. 不由语言模型给出结论、评分或判断"哪个更好"。
3. 不在默认配置下把本体内容外发给模型服务。
4. 不做依赖图分析、不推断运行期影响是否已发生。
5. 实例数据不参与对比，也不参与质检。
### 当前实现的差距（研发需要补的）
| 差距 | 说明 |
|---|---|
| 多分支对比 | 现为「一个基准 + 一个对比本体」，业务需要「一个基准 + 多个分支」并给出交叉结论 |
| 回流建议分类 | 现只输出差异清单（新增 / 修改 / 删除），缺少"建议回流 / 客户特有 / 冲突 / 无实质差异"的分类与理由 |
| 分支血缘 | 已记录 `origin_ontology_id`，但尚未用于报告中的"第几代分支""从哪个基线复制" |
| 对比报告导出 | 对比结果尚无独立报告形态（质检已有报告与下载） |
