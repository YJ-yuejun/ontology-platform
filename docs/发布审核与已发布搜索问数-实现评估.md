# 发布审核与已发布搜索问数 · 基于现有表结构的实现评估

> 配套产品设计：[11-PRD-发布审核与已发布搜索问数](prd/11-PRD-发布审核与已发布搜索问数.md)

## 1. 结论摘要

### 1.1 可行性判断

| 能力 | 基于现有结构 | 难度 | 结论 |
|---|---|---|---|
| 语义版本发布 | 已有 `ontology_releases` + 发布/评审/质检逻辑 | 低 | 可复用，需补评审身份和激活指针 |
| 共享草稿审核 | 已有 `ontologies.status` 和 change_log | 低 | 可复用 |
| 发布对象搜索索引 | 需要新增索引表和构建任务 | 中 | 建议新增，不要直接搜工作实例 |
| 关键词搜索 | SQLite FTS5 可用 | 中 | 可先做单对象类型范围 |
| 智能问数 | 需要查询计划、权限过滤、引用 | 中高 | 先做受控问题类型，不做开放 SQL |
| 多账号/RBAC | 当前没有用户表，API 无鉴权 | 高 | 生产必须做；原型可做演示身份 |
| 按人/按变更的提案分支 | 当前所有资源只有一份工作状态 | 很高 | 不建议首期做，先共享草稿+发布 |

**建议：首期做“共享草稿 + 审核发布 + 已发布索引 + 搜索问数 + 最小角色”，不做每个人一份本体、也不做完整分支系统。**

### 1.2 关键事实

- 当前后端已有 `publish`，会校验模型、质检、评审状态并生成 `ontology_releases` 快照。
- 但发布快照只含语义模型和企业资源（数据源、数据映射），**不含 object_instances**。
- 当前搜索没有全局已发布索引，页面搜索主要在各页面内过滤工作数据。
- 当前没有 `users` 表，审计 actor 默认 `manual-admin`，前端固定 `admin`；`main.py` 有 115 个路由，但没有统一鉴权中间件。
- `permission_policies` 是本体里的业务元数据，**不是登录鉴权/接口权限**，不能直接当账号权限用。
- 当前所有本体建模页看到的是同一份工作状态，没有个人草稿。

## 2. 现有表结构盘点

### 2.1 可以直接复用的表

| 表 | 现有用途 | 发布/搜索中怎么用 |
|---|---|---|
| `ontologies` | 本体主记录、status/version | 增加 active_release_id、active_index_id |
| `ontology_releases` | 已发布版本、snapshot | 保留为不可变语义版本；增加发布人/索引状态 |
| `object_types` | 对象类型、属性 JSON | 生成搜索画像、发布语义快照 |
| `link_types` | 关系类型 | 关系查询/引用/后续图谱 |
| `object_instances` | 对象记录 | **只作为建索引的数据源**，不直接对外搜索 |
| `link_instances` | 关系记录 | 关系问数/关联对象后续使用 |
| `enterprise_data_sources` | 数据源 | 记录来源系统、过滤维度 |
| `enterprise_data_mappings` | 数据映射（payload 内含 design_status/target） | 判断 searchable 属性是否已确认映射 |
| `change_log` | 工作变更与审计 | 发布 diff、提交/评审/发布审计 |
| `ontology_quality_runs` | 质检报告 | 发布门禁 |
| `business_domains` / `subject_domains` | 分类 | 搜索筛选、结果展示 |
| `interfaces` / `actions` / `business_rules` | 其他语义资源 | 语义快照、问答解释、后续权限 |

### 2.2 必须新增的表/字段

#### A. 激活版本指针

```sql
ALTER TABLE ontologies ADD COLUMN active_release_id TEXT;
ALTER TABLE ontologies ADD COLUMN active_index_id TEXT;
```

说明：

- `active_release_id`：当前对外搜索/问数的语义版本。
- `active_index_id`：当前可用索引版本。
- 发布失败不切换指针；回滚只切换指针。

#### B. 发布版本增强

```sql
ALTER TABLE ontology_releases ADD COLUMN reviewed_by TEXT;
ALTER TABLE ontology_releases ADD COLUMN published_by TEXT;
ALTER TABLE ontology_releases ADD COLUMN published_at TEXT;
ALTER TABLE ontology_releases ADD COLUMN index_status TEXT NOT NULL DEFAULT 'pending';
ALTER TABLE ontology_releases ADD COLUMN indexed_at TEXT;
ALTER TABLE ontology_releases ADD COLUMN index_error TEXT;
ALTER TABLE ontology_releases ADD COLUMN superseded_by TEXT;
ALTER TABLE ontology_releases ADD COLUMN rollback_of TEXT;
```

`index_status` 建议值：

```text
pending / building / ready / failed / stale
```

#### C. 评审记录

现有 `change_log` 可以记录“提交/通过/发布”，但无法承载逐条评审意见、驳回原因、评审人和 diff 关联。

```sql
CREATE TABLE release_reviews (
  id TEXT PRIMARY KEY,
  ontology_id TEXT NOT NULL,
  release_candidate_id TEXT,       -- 首期可以是工作状态评审批次
  reviewer TEXT NOT NULL,
  decision TEXT NOT NULL,          -- approve / reject / comment
  comment TEXT,
  model_fingerprint TEXT,          -- 防止评审后模型变化
  created_at TEXT NOT NULL
);
```

首期没有分支时，可以用一个 `release_candidate_id`（也就是本轮工作状态的评审批次）关联；后续接提案分支时复用。

#### D. 已发布对象索引

建议新增两个结构：

```sql
CREATE TABLE release_object_index (
  id TEXT PRIMARY KEY,
  release_id TEXT NOT NULL,
  object_type_id TEXT NOT NULL,
  object_type_name TEXT NOT NULL,
  instance_id TEXT NOT NULL,
  business_key TEXT NOT NULL,
  title TEXT NOT NULL,
  properties TEXT NOT NULL,        -- 只放可搜索/可展示属性
  search_text TEXT NOT NULL,       -- 标题+主键+已映射 searchable 属性
  source_system TEXT,
  quality_status TEXT,
  domain_code TEXT,
  subject_code TEXT,
  updated_at TEXT,
  indexed_at TEXT NOT NULL,
  UNIQUE(release_id, instance_id)
);

CREATE VIRTUAL TABLE release_object_fts USING fts5(
  release_id UNINDEXED,
  instance_id UNINDEXED,
  search_text,
  tokenize='trigram'
);
```

说明：

- `release_object_index` 是当前搜索读模型。
- `release_object_fts` 负责中文子串/关键词检索；`trigram` 适合中文，但数据量大时后续可替换为外部搜索。
- 索引按 `release_id` 隔离；工作状态不会进入。
- 索引数据可以按 active release 的搜索画像刷新，**不是冻结全部业务数据的快照**；语义版本不可变，数据可按同步频率更新。
- 如果要“发布时点数据也必须冻结”，需要额外的 `release_data_snapshot`；建议后续按合规要求再做，不混在语义发布里。

#### E. 账号、角色、成员

当前没有用户体系。建议最小表：

```sql
CREATE TABLE users (
  id TEXT PRIMARY KEY,
  username TEXT NOT NULL UNIQUE,
  display_name TEXT NOT NULL,
  email TEXT,
  status TEXT NOT NULL DEFAULT 'active',
  auth_provider TEXT,              -- sso / local-demo
  external_subject TEXT,           -- SSO subject
  created_at TEXT NOT NULL,
  last_login_at TEXT
);

CREATE TABLE ontology_members (
  ontology_id TEXT NOT NULL,
  user_id TEXT NOT NULL,
  role TEXT NOT NULL,              -- owner/editor/reviewer/publisher/analyst/auditor
  granted_by TEXT,
  created_at TEXT NOT NULL,
  PRIMARY KEY (ontology_id, user_id, role)
);
```

如果首期用 SSO：

- `users` 只做本地映射和审计。
- 登录由企业 OIDC/SAML 完成，不自建密码。
- 组织组映射到 `ontology_members.role`。

如果首期没有 SSO：

- 建议只做“演示身份切换”（建模人/评审人/发布人/分析师），并在 UI 标“仅演示”。
- 不要把演示身份当成生产安全边界。

### 2.3 现有发布数据的迁移

当前数据库里已有 3 条 `ontology_releases`，但 `ontologies.status` 可能仍处于 draft（发布后派生了工作状态），因此不能只看 ontology.status 判断“有没有发布”。

迁移步骤：

```text
1. 为每个有历史 release 的本体，取 created_at 最新的一条 published release
2. 写入 ontologies.active_release_id
3. 用该 release 的语义+映射快照构建一次索引
4. 索引成功后写入 ontologies.active_index_id
5. 没有 release 的本体保持 active_release_id = NULL；搜索显示“尚未发布”
```

关键点：

- 判断是否可搜索，看 `active_release_id`，不看 `ontologies.status`。
- 工作状态可以是 draft，但只要 active release 存在，已发布搜索仍可用。
- 派生新工作状态不应清空 active release。

### 2.4 暂时不要动的表

- 不要给每张资源表加 `branch_id`/`proposal_id`。这是完整分支系统的改造量，首期不值得。
- 不要把 `permission_policies` 当登录权限表。它是业务语义里的权限策略资源，和平台鉴权是两件事。
- 不要给每个用户复制一套 `object_types`/`link_types`。

## 3. 发布实现方法

### 3.1 现有流程

```text
draft
  → submit_review（校验 + 质检）
  → in_review
  → approve（评审通过）
  → reviewed
  → publish（生成 ontology_releases 快照）
  → published
```

### 3.2 建议改造后的流程

```text
draft
  → submit_review
      校验 + 质检 + 映射覆盖 + 评审人指定
  → in_review
      release_reviews 记录意见
  → approve / reject
  → approved
  → publish_semantic
      生成不可变语义版本
  → build_index
      生成 release_object_index + FTS
  → activate
      切换 ontologies.active_release_id / active_index_id
  → active
```

如果索引失败：

```text
build_index failed
  → release.index_status = failed
  → active 指针不切换
  → 旧版本继续服务
  → 允许重试/回滚
```

### 3.3 需要改的后端模块

| 模块 | 改动 |
|---|---|
| `repository.publish` | 拆成 semantic release + index build + activate 三段 |
| `governance_insights` | 增加映射覆盖、搜索画像校验、发布快照的索引元数据 |
| 新增 `release_service` | 提交/评审/发布/重试/回滚状态机 |
| 新增 `search_index_service` | 从 object_instances + mappings 构建索引 |
| 新增 `published_search` | 只读 active release 索引的查询 |
| 新增 `qa_service` | 查询计划、校验、聚合、引用 |
| 新增 `auth` | 当前用户、角色、权限守卫 |
| `enterprise.py` | 映射状态、资源发布状态、审计 actor 接账号 |

### 3.4 发布门禁（关键）

当前 `publish` 已做：

- 待发布变更非空
- 模型校验
- 质检通过且 fingerprint 未变化
- `reviewed` 状态

新增：

1. **映射覆盖率**
   - 每个对象类型的 title property 必须有已确认映射。
   - 每个 `is_searchable=true` 的属性必须有已确认映射。
   - 没有映射的 searchable 属性：阻断，或在发布评审中显式标记“从搜索画像排除”。
2. **搜索画像**
   - 没有标题属性/业务主键的对象类型不能进入搜索。
   - 没有实例的对象类型可以发布，但索引为空。
3. **评审身份**
   - reviewer 不能等于 submitter（默认）。
   - publisher 不能缺少 publisher 角色。
4. **索引可用**
   - semantic release 生成后必须索引成功，才切换 active。

## 4. 搜索实现方法

### 4.1 查询路径

```text
用户输入
  → 读取 active_release + active_index
  → 权限过滤允许的对象类型
  → release_object_fts MATCH 关键词
  → join release_object_index 过滤
  → 排序/分页/snippet
  → 结果卡
```

### 4.2 为什么用 FTS5

- 当前 SQLite 已验证支持 FTS5。
- 中文可用 `trigram` tokenizer 做子串检索；比 `LIKE '%词%'` 更适合逐步扩展。
- 数据量到百万级/需要高亮、分词、同义词时，再换外部搜索。

### 4.3 搜索结果要素

- 对象类型 + 标题
- 业务主键
- 已发布版本
- 匹配属性摘要
- 来源系统、更新时间、质量状态
- 打开对象 / 问 AI

### 4.4 搜索权限

- 先按对象类型做 ACL；分析师只能查 active release。
- 行级/字段级后续；不要在 SQL 里先查出再前端过滤。
- 问数使用同一套过滤后的索引。

### 4.5 映射版本必须跟 release 绑定

这是实现时最容易做错的地方：

- 发布评审检查的是**当前工作状态的 data_mappings**。
- 发布时应把这一版映射一起写入 `ontology_releases.snapshot`（现有 snapshot 已包含 enterprise_resources）。
- 建索引必须使用 **该 release 快照里的对象属性 + 映射**，不能使用当前工作区的最新映射。
- 否则发布后有人改了映射，旧版本的搜索结果会悄悄变化。
- 数据刷新可以继续使用 release 快照里的映射版本。

### 4.6 数据新鲜度

建议明确：

- **语义版本冻结**：对象/属性/映射定义不随工作草稿改变。
- **数据索引可刷新**：当前业务数据按同步频率更新索引。
- 页面展示“索引时间/数据截止时间”。
- 如果合规要求“发布时点数据冻结”，再增加 `release_data_snapshot`，不要把它和语义发布混为一谈。

## 5. 智能问数实现方法

### 5.1 不做的事

- 不让 LLM 直接生成/执行 SQL。
- 不让 LLM 自己数记录。
- 不查工作状态、未映射数据、未发布对象。
- 不跨本体。

### 5.2 推荐链路

```text
问题
  → 意图识别（查记录/计数/分组/对比/关系/定义）
  → 绑定 active release 的对象/属性/映射
  → LLM 输出受约束的查询计划 JSON
  → 后端校验对象/属性/操作符/聚合
  → 权限过滤
  → 查 release_object_index / SQL 聚合
  → 生成带引用的回答
```

查询计划只允许：

- 单对象类型（MVP）
- 已验证的属性
- `eq/contains/range/in`
- `count/group_by`
- 简单关系查询（第二阶段）

### 5.3 引用

- 回答带对象类型、业务主键、标题、发布版本、索引时间。
- 统计回答带聚合口径，不列假记录。
- 无结果明确说明，不生成假数据。
- 用户可展开“执行了什么查询”。

## 6. 权限体系设计

### 6.1 角色

| 角色 | 建模 | 提交评审 | 评审 | 发布/回滚 | 搜索/问数 | 审计 |
|---|---:|---:|---:|---:|---:|---:|
| 平台管理员 | 管理 | - | - | - | 管理 | 管理 |
| Ontology Owner | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Editor | ✓ | ✓ | - | - | - | - |
| Reviewer | - | - | ✓ | - | - | - |
| Publisher | - | - | - | ✓ | - | - |
| Analyst | - | - | - | - | ✓ | - |
| Auditor | - | - | - | - | - | ✓ |

规则：

- 默认 `submitter != reviewer`。
- `reviewer != publisher` 可选；高风险建议分离。
- Owner 可覆盖，但必须审计。
- Editor 不能直接发布。
- Analyst 不能读工作状态。
- Auditor 只看审计/发布记录，不看业务数据。

### 6.2 权限落点

| 层 | 权限 |
|---|---|
| 平台 | 登录、平台管理员 |
| 本体 | owner/editor/reviewer/publisher/analyst/auditor |
| 对象类型 | 读/写/搜索（MVP 先按本体角色） |
| 行/字段 | 后续 |
| 发布操作 | reviewer/publisher 分离 |
| 搜索/问数 | 只读 active release；按对象类型过滤 |

### 6.3 认证方式建议

**生产：企业 SSO（OIDC/SAML）+ 组织组映射角色。**

- 不自建密码、不自己维护密码找回。
- 后端统一中间件解析当前用户。
- 所有写接口必须带用户和 ontology 角色校验。
- 发布/回滚必须二次校验 publisher 角色。
- 审计记录使用用户 ID，不再默认 `manual-admin`。

**没有 SSO 的私有化：**

- 本地账号 + 强密码哈希 + 会话 + 登录限流 + 审计。
- 仅作为临时方案，不建议长期维护。

**原型演示：**

- 可以做身份切换，但 UI 必须标“演示身份，不是安全边界”。
- 不能把演示切换当作上线后的权限体系。

### 6.4 当前 `permission_policies` 的定位

`enterprise_permission_policies` 里的角色/资源/动作权限是**本体语义内容**，用于表达业务权限策略，不是当前平台登录/API 权限。

不要直接用它的 `role` 字段来登录鉴权。否则：

- 业务人员可以修改权限策略来提权；
- 发布审核角色和业务角色混在一起；
- SSO 组织组无法稳定映射。

平台权限单独建 `users`/`ontology_members`；业务权限策略后续可作为数据行权限的来源，但必须由平台身份映射。

## 7. 工作量评估

> 估算按当前代码基础、1 名熟悉代码的开发，包含前后端、迁移、测试，不含部署/SSO 组织协调。

| 工作项 | 难度 | 估算 |
|---|---|---:|
| 激活指针/发布版本字段/迁移 | 低 | 1–2 天 |
| 评审记录/评审状态/权限门禁 | 中 | 3–5 天 |
| 映射覆盖 + 搜索画像 + 发布门禁 | 中 | 2–3 天 |
| 索引构建 + FTS + 刷新/重试 | 中 | 3–5 天 |
| 搜索页 + 过滤/结果/引用 | 中 | 3–5 天 |
| 智能问数查询计划 + 校验 + 引用 | 中高 | 5–8 天 |
| 账号/角色/SSO 接入 | 高 | 5–10 天 |
| 发布/评审/搜索前端页面 | 中 | 5–7 天 |
| 测试/迁移/回归/文档 | 中 | 4–6 天 |

**MVP 总量：约 25–40 人日（5–8 周，单人）；两人并行约 3–4 周。**

如果首期简化：

- 共享草稿 + 单管理员演示 + LIKE 搜索 + 只做 2–3 个对象类型：
  - 约 12–18 人日。
- 但这不是生产权限闭环，只能作为演示/POC。

## 8. 推荐落地顺序

### Sprint 1：发布边界

- 增加 active release/index 指针。
- 发布语义版本 + 索引状态 + active 切换。
- 索引失败不切流。
- 映射覆盖门禁。
- 发布/回滚审计。

### Sprint 2：账号与审核

- `users`/`ontology_members`。
- SSO 或演示身份。
- Reviewer/Publisher 角色。
- 评审意见、驳回、默认禁止自审。
- 发布确认页。

### Sprint 3：搜索

- 索引构建/刷新。
- 搜索页、对象类型/域/来源/状态筛选。
- 结果卡、版本徽标、索引时间。
- 搜索权限过滤。

### Sprint 4：问数

- 查询意图/查询计划。
- 计数、分组、筛选、单对象关系。
- 引用、查询回放、无结果处理。
- 权限与审计。

### 暂不做

- 按人/按变更的完整分支系统。
- 行级/字段级权限。
- 多级会签/逐资源审批。
- 实时同步、向量检索、跨本体问数。
- AI 自动执行写操作。

## 9. 核心风险

| 风险 | 影响 | 处理 |
|---|---|---|
| 语义发布成功但索引失败 | 搜索不可用 | active 不切换，旧索引继续服务 |
| 索引数据未绑定 release | 工作数据泄漏 | 查询强制 active release；索引只读 |
| searchable 属性未映射 | 搜索漏数据/口径错误 | 发布门禁 + 搜索画像 |
| 只有 admin | 审核发布无责任分离 | 多账号 + 角色 |
| 模型编造记录 | 问数不可信 | 只引用检索结果，统计走聚合 |
| 数据量/中文检索 | 性能/召回差 | FTS5 trigram 起步，后续外部搜索 |
| 发布后数据变化 | 结果与“发布版本”不一致 | 明确语义冻结/数据可刷新，显示数据截止时间 |

## 10. 需要拍板的决策

1. **个人草稿还是共享草稿？**
   - 首期建议共享草稿；多人并行时再上变更提案。
2. **发布数据是冻结快照还是可刷新索引？**
   - 建议语义冻结、数据索引可刷新；如合规要求，再加快照。
3. **“已映射”是标题映射即可，还是全部 searchable 属性？**
   - 建议标题/主键 + searchable 属性全部已确认，否则阻断或排除该属性。
4. **SSO 是否已具备？**
   - 有 SSO：直接接；没有：原型演示身份，生产前补。
5. **首期搜索范围？**
   - 建议先选 3–5 个核心对象类型，不要全量上线。
6. **是否允许自审？**
   - 默认不允许；高风险双人。

## 11. 最终建议

- **不要每个人一份本体副本。**
- 首期：**共享工作草稿 + 评审 + 语义发布 + 已发布索引 + 搜索问数 + 最小角色**。
- 生产：**SSO + 角色分离 + 发布门禁 + 索引回滚**。
- 多人并行成为瓶颈后，再升级为**按变更提案隔离**，不是按账号复制。
- 搜索/问数只读 active release，绝不读工作草稿。
