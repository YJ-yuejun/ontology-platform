# 整体复制本体（分支）功能

产品方向：**去掉"版本"概念**。本体建好之后要迭代，就整体复制一份出来，用**本体名**区分分支（`资产本体_copy`、`资产本体v2`），然后在分支上改；要比较就看两个本体的差异。

## 为什么不能沿用原来的"导出 → 导入"

原型的 `export_ontology` / `import_ontology` 是给数据包迁移用的，**对两个真实本体实测都跑不通**：

| 问题 | 原因 |
|---|---|
| 报"映射数据源必须选择当前本体已登记的数据源" | 导入顺序是 `对象类型 → … → 企业资源`，**数据源排在最后**；而带 `backing_source` 的对象在创建时就会校验数据源必须已存在 |
| 报"主题域必须属于对象选择的业务域" | 模板里的"业务域"是旧口径（`管网`、`经营`…），平台两级分类是另一套（`管网运营域`…），直接照搬会被校验拒绝 |
| 所有资源都拿新 UUID | 若用 UUID 做匹配键去对比，副本会被报成"整本删除 + 整本重建"（实测 70 个资源产生 62 条假差异） |
| 丢模板证据 | 创建接口只按固定字段重建 `metadata`，`template_raw` / `template_row` 等是模板导入**事后补**的；复制时若不补，分支就失去模板可追溯性 |

## 实现

`POST /api/ontologies/{ontology_id}/copy`，body 可选 `{name, namespace}`；
留空则默认 `原名_copy` + 命名空间加 `.copy` 后缀。核心在 `repository.copy_ontology()`。

### 复制顺序（这是关键）

```
本体 → 业务域 → 主题域
     → 数据源、治理资产        ← 必须先于对象类型
     → 接口                    ← 必须先于对象类型
     → 对象类型 → 关系类型 → 动作类型 → 业务规则
     → 其余企业资源（映射、规则与函数、能力、执行映射、权限策略、场景）
     → 对象实例 → 关系实例
```

### 保真处理

| 处理 | 说明 |
|---|---|
| 业务标识保留 | `name` / `code` / 模板 ID 原样保留，只有 UUID 换新 → 「本体对比」能按业务标识配对 |
| 模板证据随行 | 对象类型 / 关系类型 / 动作类型 / 业务规则复制后，把源 `metadata` 里创建接口覆盖不到的字段（`template_raw`、`template_row`、`template_sheet`…）补回去 |
| `metadata` 严格对齐 | 源里没有、而创建接口按模型默认值补出来的键（例如 `is_core=False`）会删掉，副本不凭空多出字段 |
| 引用重映射 | 主题域 / 接口 / 关系端点 / 动作与规则目标 / 实例引用全部改指副本内部；空值（`None` / `""`）原样保留，不因为 `.get("")` 变成 `None` 而凭空产生差异 |
| 既有绑定放行 | 模板业务域与平台分类不一致时，按源对象的既有绑定放行（与 `update_object_type` 同口径），不改写模板原值 |
| 分支来源 | `ontologies.origin_ontology_id` 记录从哪个本体复制而来（`_ensure_column` 幂等迁移） |

### 不复制的内容

发布版本、变更记录（`change_log` / `mdl_ver_chg`）、质检报告、智能构建提案与会话、
场景运行记录、智能体交互、**数据源连接密码**、结构快照、智能构建证据、模板原始行
（`template_records`；每个对象的 `metadata.template_raw` 已随对象复制）。

这些是**原体的历史与运行痕迹**，不是本体的语义定义；分支应该从干净状态开始。

## 前端入口

本体工作台 → 资源目录头部 → **复制为分支**。弹窗里确认新名称与命名空间，
并明确列出"会复制 / 不会复制"的范围；提交后自动刷新本体列表并跳转到新分支。

## 验证

| 验证项 | 结果 |
|---|---|
| 复制管道运输运营本体 | 9 对象 / 10 关系 / 4 动作 / 2 规则 / 3 实例 / 2 业务域 / 4 主题域 / 5 数据源 / 7 治理资产 / 14 映射 / 4 规则函数 / 3 能力 / 3 执行映射 / 4 权限策略 / 2 场景 —— **逐项与原体一致** |
| 复制采购与财务协同本体（带 2 个接口、13 个带来源的对象） | 同上，全部一致；`backing_source` 与接口实现均保留 |
| **跨本体对比 原体 vs 副本** | 两个本体都是 **0 差异**（0 新增 / 0 修改 / 0 删除） |
| 模板证据 | 对象类型 / 关系类型 / 动作类型 / 业务规则的 `metadata` 与源**完全一致** |
| 资源 ID | 全部换新，不与源重叠 |
| UI 流程 | 按钮 → 弹窗默认值 → 提交 → 跳转新分支，无 JS 异常 |
| 自动化 | 新增 `test_copy_ontology_reproduces_the_built_in_pipeline_ontology_without_a_single_diff`（含资源数、ID 换新、引用改指、模板证据、零差异断言）；后端 45/45、前端 35/35 通过 |

## 顺带修掉的一个对比侧缺陷

跨本体对比原来把"缺键"和"值为 null"当成不同：副本经 Pydantic 序列化会补出
`template_id=None` 这类键，而原体原始 JSON 里根本没有 → 被误报成 26 处"已修改"。
现在在 `_drop_none()` 里统一视为"未设置"。**只在跨本体对比生效**，不动
`_semantic_index`，避免改变模型指纹让既有质检报告集体失效。
