# 动作管理 v2 精简设计提案

状态：业务定义精简方案已实现；实际字段及交互以《12-PRD-动作管理v1.0.md》内 v2.0 内容为准。旧数据保留，不进行破坏性迁移。

## 结论

当前 14 个填写字段混合了业务定义、技术执行和维护治理，折叠不足以解决语义重叠。建议业务建模入口默认只有 4 个字段，并按实际需要添加“所需信息”和“执行前提”。接口绑定、审批权限和维护信息在详情的独立入口处理，不再作为新建动作必须逐项理解的内容。

这是针对当前“文字描述、定义管理”阶段的产品设计，并非 Palantir 官方表单，也不是完整执行引擎设计。

## 文档研究依据

1. [Palantir Action types](https://www.palantir.com/docs/foundry/action-types/overview)：动作类型定义对象、属性及关系的变更和提交时的副作用；一个动作可以涉及多个对象。本阶段仍允许选择一个主要作用对象，不能将它理解成未来完整影响范围。
2. [Rules](https://www.palantir.com/docs/foundry/action-types/rules)：这里的 Rules 是把参数转换成对象编辑或其他效果的执行规则，不是自动触发动作的规则。
3. [Submission criteria](https://www.palantir.com/docs/foundry/action-types/submission-criteria)：描述动作能否提交的条件，与动作类型自身的编辑权限不同。
4. [Parameters](https://www.palantir.com/docs/foundry/action-types/parameter-overview)：参数可以来自用户或应用，也可以隐藏；不能要求用户重复填写所有已知上下文。
5. [Side effects](https://www.palantir.com/docs/foundry/action-types/side-effects-overview)：通知与外部系统调用有专门配置，不必让业务人员另写几段重复的结果说明。

据此提出本地产品边界：动作定义负责“业务操作是什么”；调用方负责“什么时候发起”；执行配置负责“如何接系统和修改数据”。

## 默认新建表单

| 字段 | 方式 | 要求 | 口径 |
|---|---|---|---|
| 动作名称 | 单行文本 | 必填 | 动词加业务对象，例如发布负载预警 |
| 作用对象 | 对象名称下拉 | 必填 | 选择主要作用对象，后台关联 ID |
| 操作说明 | 多行文本 | 草稿可空，确认业务定义前必填 | 说明这个动作做什么；不要求提供算法或接口实现 |
| 预期结果 | 多行文本 | 选填 | 说明成功后的主要变化或产物；原“结果、对象变化、联动”的业务说明集中在此，可分行填写 |

创建只要求名称和作用对象，以便先登记现有数据。业务定义确认需补全操作说明，但不意味着可执行。保存由系统生成不可变 ID/API 名称，并自动标记为草稿。历史业务编号保持原值，导入仍支持外部编号。

合并业务描述的展示不等于合并执行时的结构化契约。真正执行时，对象修改、返回值、通知仍须分开配置和校验。

## 按需增加的两项

- 所需信息：点击“添加所需信息”后逐条填写，例如日期、业务组、原因；当前只作业务说明。未来接入执行时再补充字段类型、来源和校验；从对象上下文已能获得的信息不要求用户重复输入。
- 执行前提：点击“添加执行前提”后逐条填写，例如方案已获确认。用户自填，不从规则目录选择；只说明允许操作的前提，不意味着系统会自动监控或发起。当前多行文本也不自动推断 AND/OR 逻辑。

不再同时提供“触发规则”和“触发条件”两个文本入口。但不能机械合并历史值：规则名称可能不是完整判断条件，旧“触发条件”也可能描述外部事件而非执行门槛，需要保留原语义后确认归属。

## 当前字段去向

| 当前字段 | v2 处理 |
|---|---|
| 动作 ID | 系统生成，详情只读，导入保留外部编号 |
| 动作名称 | 保留 |
| 动作类型 | 从业务新建表单移除；当前 business/control/notify/calculate/manual 混合领域、效果、实现与调用方式，不能作为排他的执行分类；保留历史数据 |
| 作用对象 | 保留，选名称，存 ID |
| 触发规则 | 取消独立输入框；新输入采用“执行前提”。旧规则名称/ID 留在来源记录，不自动当成条件 |
| 触发条件 | 按语义区分执行前提与外部发起事件；前者归执行前提，后者留作场景/流程触发说明 |
| 执行逻辑 | 业务文字部分作为“操作说明”；已有公式/API 配置保留在执行配置，不能丢弃 |
| 执行结果/输出 | 作为“预期结果”，不要将定义中的结果误当成某次实际执行结果 |
| 对象/属性变化 | 业务说明合入预期结果，既有结构化编辑定义继续独立保存 |
| 副作用/联动 | 业务说明可在预期结果里分行写；实际通知、webhook 等留在执行配置 |
| 输入参数 | 改为按需添加“所需信息”，已有参数类型等元数据完整保留 |
| 是否需要审批 | 移到详情“审批与权限”入口，缺失时仍为待确认；不允许精简界面导致原有审批约束被清除 |
| 责任人 | 移到维护信息；创建人自动记录，但不自动等同于业务责任人 |
| 建模状态 | 从下拉改为生命周期操作；保存为草稿，明确操作才确认；不依据填写完整就声称动作可运行 |

## 页面方案

列表默认显示：动作名称（下方 ID）、作用对象、预期结果摘要、建模状态、更新时间、操作。详细的条件和规则文本不再挤进列表。

点击打开可关闭的详情：主区域显示业务定义；存在所需信息和执行前提时展示；独立入口访问执行配置、审批与权限、维护信息和来源记录。未实现的执行配置不展示成已具备能力的按钮。

创建表单默认四项，不再将原有 14 项分别塞进四个折叠组。底部两个按需添加入口，保持自填多条的习惯。

例（拟写文案，仅演示产品，不自动写入模型）：
- 动作名称：发布负载预警。
- 作用对象：预警事件。
- 操作说明：发布已识别的负载预警信息。
- 预期结果：形成可供调度人员查看的预警通知。
- 执行前提：负载等级达到关注及以上（这只是可用前提；自动发起策略另行配置）。

## 现有样例需要单独确认的语义

- ACT-001 发布负载预警与 ACT-008 推送预警通知可能重叠。若前者创建/发布预警事件、后者发送消息，则可保留两个动作；若都只发送同一通知，才考虑合并。不能仅凭名称自动合并。
- ACT-007 调度效果预演若只是返回计算结果、不修改对象或产生业务副作用，更接近计算能力/函数。若保存预演方案和结果，也可作为业务动作。先明确业务结果，不增加一个随意选择的“计算动作”分类来回避问题。
- 主要作用对象可以不是唯一被修改的对象；后续执行配置中应描述完整影响范围。

## 数据兼容与实施次序

1. 先实施表单和列表精简、自动 ID、两个按需添加入口；不删表或清空历史字段。
2. 旧执行逻辑有值时可预填操作说明；空值保持空，不根据动作名称杜撰逻辑。
3. 结果、对象变化、联动以带来源标签的方式展示候选合并内容，原字段保持，编辑确认后保存新版业务描述；禁止纯字符串拼接后覆盖原始证据。
4. 旧规则名称和编号留在来源区，旧条件原文保留；不自动将“次日数据可获取”等外部事件转换成执行校验。
5. 业务确认和可执行状态分开。当前仅完成业务定义，不新建虚假的“可执行”状态。
6. 真实执行阶段，再在已有动作映射/能力模块补参数来源、系统调用、对象修改、结果校验和审批策略；提交执行前必须满足相应配置要求。

## 验收

- 新建默认四个字段，名称和作用对象即可保存草稿；对象选择只显示名称。
- 所需信息与执行前提按需添加、支持多条，可全部删除。
- 不出现相邻的“触发规则/触发条件”文本框，也不要求逐一填写“输出/对象变化/副作用”。
- 导入的 10 个动作、原始 ID 和来源证据不丢失；旧参数、公式/API、审批约束保持原值。
- 建模确认不等于可执行；纯文字描述不会调用外部系统。
