# 本体建模中心原型问题 QA

> 文档版本：v1.0  
> 评审日期：2026-09-08  
> 评审对象：企业本体 Studio 高保真原型 v1.9  
> 用途：统一产品、研发与算法团队对业务域、对象、关系、动作、数据映射和执行接口的理解。

## 一、总体结论

当前原型已经具备本体、业务域、主题域、对象类型、关系类型、接口、规则、动作、数据映射和治理发布等核心结构，但仍有三类概念需要进一步拆清：

1. 本体版本状态、资源使用状态、业务实例状态和演示数据标记不应共用一套枚举。
2. 对象属性、关系属性、接口属性和动作参数不应完全复用同一个属性编辑器。
3. 动作的参数、提交条件和真实接口执行映射需要形成可执行契约，不能只保存说明文本。

建议决策汇总：

| 项目 | 结论 |
|---|---|
| 业务域、主题域状态 | 保留但简化为“启用/停用”，不与发布状态混用 |
| 对象分类 | 删除当前必填分类；如需保留，拆成对象形态和数据角色 |
| 关系类型状态 | 保留“试用/启用/弃用”，删除“示例”状态 |
| 关系属性 | 保留为高级能力，补齐关系实例和映射交互 |
| 图谱域筛选 | 增加业务域、主题域联动筛选和高亮 |
| 动作参数 | 保留，但使用专用参数编辑器 |
| 动作提交条件 | 默认 AND，并支持显式条件组；不得直接执行任意 SQL |
| 来源字段 | 从通用属性编辑器移除，集中到数据映射层 |
| 动作接口绑定 | 通过“动作→执行映射→系统能力→执行网关”实现 |

## Q1：业务域和主题域的“状态”参数是什么？设计逻辑是什么？

### A

当前原型中的状态表达的是业务域或主题域这个“分类资源”是否稳定、是否允许继续使用，而不是本体版本状态，也不是业务数据实例状态。

当前状态大致包含：

| 状态 | 原本含义 |
|---|---|
| 试验中 | 分类仍在验证，暂不建议作为稳定生产口径 |
| 已启用 | 可以正式用于归类对象类型 |
| 已弃用 | 保留历史兼容，不建议再分配新对象 |
| 示例 | 用于标记演示资源 |

当前设计存在以下问题：

- “示例”不是生命周期状态，应该是数据来源或演示标记。
- 业务域、主题域状态没有形成完整的父子约束。
- 容易和本体的“设计中→待评审→评审通过→已发布”混淆。
- 停用父级业务域时，没有完整展示对子主题域、对象、关系和场景的影响。

### 建议

- 字段名称改成“使用状态”。
- 业务域和主题域一期只保留“启用、停用”。
- 设计、评审和发布状态统一由本体工作状态管理。
- “是否演示资源”独立管理，不进入状态枚举。
- 停用业务域或主题域前展示影响分析，并生成显式变更记录，不能静默级联。

## Q2：对象类型的创建步骤是什么？“对象分类”是否需要？

### A

当前对象类型创建分为三步：

1. 对象身份：显示名称、稳定标识、对象分类、状态、图标和业务定义。
2. 对象结构：属性、唯一主键和标题属性。
3. 分类与实现：所属主题域、实现接口和映射数据源。

建议下一版调整为：

1. **定义业务身份**：显示名称、稳定标识、业务定义、负责人。
2. **归入业务分类**：选择业务域和主题域，明确业务边界。
3. **定义对象结构**：唯一主键、标题属性、状态属性、普通属性和约束。
4. **配置接口与数据实现**：实现接口、数据源和映射完整度。
5. **检查并保存**：检查主键、主题域、接口契约和映射引用。

当前“对象分类”包含业务实体、业务单据、业务任务、业务事件和主数据，这些选项并不处于同一个分类维度：

- 供应商既是业务实体，也可能是主数据。
- 合同既是业务实体，也可以被视为业务单据。
- 告警既是业务事件，也可能有独立实例、状态和动作。

### 建议

一期从必填项中删除当前“对象分类”。如果业务确实需要，应拆成两个可选维度：

- 对象形态：实体、事件、任务/工作项。
- 数据角色：主数据、交易数据、参考数据、事件数据。

只有当分类能够驱动图标、默认属性、权限、同步策略或智能体行为时，才值得进入正式元模型。

当前“所属主题域”允许暂不分类，但发布检查又会阻止未分类对象提交评审。界面应明确提示：对象可以暂存，但提交评审前必须归入主题域。

## Q3：关系类型的生命周期参数是什么？“示例”状态是否需要？

### A

关系类型状态描述的是关系定义本身是否稳定可用。例如：

- `合同→签约方→供应商`可以是已启用关系。
- 被新版关系替代的`合同→对应→供应商`可以进入已弃用状态。

当前原型已经实现两项有效约束：

- 已启用关系的两端对象必须已经启用。
- 已启用关系不能直接删除，需要先弃用。

但“生命周期状态”这一名称容易被误解为关系实例的业务生命周期。

### 建议

- 字段改名为“使用状态”或“资源状态”。
- 保留“试用中、已启用、已弃用”。
- 删除“示例”状态；演示资源使用独立标记或演示数据包管理。
- 对象弃用导致关系受影响时，先展示影响清单，再由用户确认一组显式变更，不能后台静默修改。

## Q4：关系属性是什么意思？和对象属性有什么区别？

### A

对象属性属于某个对象自身；关系属性属于两个对象实例之间的某一次连接。

例如：

```text
员工
- 员工编号
- 姓名
- 所属部门
```

这些是对象属性。

```text
员工 ─参与→ 项目
- 项目角色
- 参与开始时间
- 投入比例
```

“项目角色、开始时间、投入比例”只对“某员工参与某项目”这条关系有意义，因此属于关系属性。

采购领域还可以表示为：

```text
供应商 ─供应→ 物料
- 协议价格
- 生效时间
- 供应优先级
```

关系属性常用于：

- 多对多关系；
- 生效时间和失效时间；
- 金额、比例、角色、顺序；
- 关系来源、证据和置信度；
- 两个实例之间特有、但不属于任意一端对象的信息。

如果一条关系开始拥有独立编号、业务状态、审批流程、生命周期或动作，就不应继续堆关系属性，而应将它建成关联对象。例如“员工参与项目”如果需要独立审批、考勤和结算，可以建成“项目任职”对象。

### 当前原型问题及建议

后端可以保存关系实例属性，但前端还没有完整覆盖关系实例属性的维护和映射。因此建议：

- 保留关系属性，但放入“高级配置”。
- 增加“何时应改建关联对象”的说明。
- 补充关系实例属性的查看、编辑和数据映射。
- 在运行能力补齐前，避免普通用户大量配置关系属性。

## Q5：模型图谱是否需要业务域和主题域筛选？

### A

需要。业务域和主题域非常适合作为图谱筛选和观察维度，但不建议默认画成普通业务对象节点。

推荐交互：

1. 第一级选择业务域。
2. 第二级联动选择主题域。
3. 默认采用高亮模式，而不是直接隐藏其他对象。
4. 当前域内对象保持原色，域外对象降低透明度。
5. 跨业务域关系使用特殊颜色或边界标记。
6. 提供“只看当前范围”开关。
7. 显示当前范围的对象数、内部关系数和跨域关系数。

后端图谱接口需要为节点补充业务域和主题域的 ID、名称；前端再实现级联筛选、高亮和隔离模式。

## Q6：动作类型的参数在整个过程中有什么价值？

### A

动作参数是动作的输入契约，不是动作是否允许执行的判断条件。

例如“暂停运输任务”动作可以包含：

```text
暂停原因：必填文本
暂停截止时间：可选时间
操作方式：人工暂停/系统风控
期望对象版本：防止并发覆盖
```

动作参数用于：

- 在执行前校验输入是否合法；
- 告诉智能体或操作表单需要收集哪些信息；
- 将本体业务参数映射为外部系统接口参数；
- 定义类型、枚举、必填、默认值和校验范围；
- 支持审计、幂等和并发控制。

参数值可以来自用户填写、当前对象属性、关联对象、规则结果、当前用户上下文或系统默认值。

### 当前原型问题及建议

当前动作参数复用了对象属性编辑器，因此出现了“来源字段、可检索”等不适用于动作参数的配置。应拆成专用动作参数编辑器，至少包含：

- 参数名称和稳定标识；
- 数据类型、是否必填、默认值；
- 参数来源；
- 枚举或校验约束；
- 是否敏感；
- 是否参与幂等计算。

## Q7：多个动作提交条件之间是 AND 还是 OR？条件表达式是调用接口还是执行 SQL？

### A

当前原型没有明确规定多个条件的组合关系，后端也只是保存条件列表，本体智能体演示没有真正执行这些条件。这部分目前不具备生产可执行性，必须调整。

推荐规则：

- 默认多个条件使用 AND。
- 页面明确显示“满足以下全部条件”。
- 支持切换“满足全部（AND）/满足任一（OR）”。
- 复杂规则使用条件组表达嵌套 AND/OR。
- 普通用户通过字段、运算符和值的结构化表单配置，不直接输入任意代码。

例如：

```text
满足全部条件：
1. 运输任务状态 = 执行中
2. 当前用户拥有“运输调度”角色
3. 不存在正在审批的暂停申请
```

条件表达式不应该直接执行 SQL，也不应该被解释成接口地址。推荐通过受限规则语言或已登记规则表达：

```text
object.status == "执行中"
actor.hasRole("运输调度")
rule.no_pending_suspend_request == true
params.reason != null
```

如果条件必须读取外部系统，应调用已登记的只读规则函数或系统能力，再将其结果用于判断。SQL只能存在于受治理的数据服务或规则函数内部，不能直接放进动作定义。

标准执行顺序：

```text
校验动作参数
→ 获取对象及关系上下文
→ 执行提交条件
→ 校验权限
→ 人工确认或审批
→ 调用执行映射
→ 验证执行结果
→ 记录审计
```

## Q8：配置中的“来源字段”是什么？为什么有些地方是选填？

### A

来源字段表示底层物理数据中，为某一本体属性提供值的字段。

例如：

```text
财务系统.payment_request.apply_amount
                ↓ 数据映射
付款申请.applyAmount
```

它的价值是让本体属性可以追溯到真实数据来源，并在底层字段变化时只修改映射，不影响上层对象和智能体契约。

当前原型把“来源字段”放进了通用属性编辑器，因此它同时出现在对象属性、接口属性、关系属性和动作参数中。这是组件复用造成的设计问题。

建议按场景拆分：

| 配置位置 | 是否需要来源字段 | 推荐处理 |
|---|---|---|
| 对象属性定义 | 不直接填写 | 统一到数据映射页配置 |
| 接口属性 | 不需要 | 接口只声明语义和结构契约 |
| 关系属性 | 不直接填写 | 使用关系映射配置 |
| 动作参数 | 不使用该名称 | 改成“参数来源” |
| 数据映射 | 需要 | 表示物理列、JSON路径或响应字段 |
| 动作执行映射 | 需要路径概念 | 改成“请求参数路径/结果字段路径” |

对象可以先完成概念建模而暂不连接真实数据，所以对象层映射可以为空；但一旦创建正式数据映射，相应字段就应完整：

- 对象主键通过属性映射表达：来源表、来源主键字段和目标对象主键属性必填；当前不单设“对象映射”类型。
- 属性映射：来源字段、目标对象和目标属性必填。
- 关系映射：来源关联键、目标关联键必填。
- API或文档映射：填写JSON路径、响应路径或抽取规则。

## Q9：动作如何绑定真实业务操作接口？

### A

动作不应直接填写真实接口地址，推荐采用四层结构：

```text
本体动作
   ↓ 动作执行映射
系统能力
   ↓ 执行网关/连接器
真实业务系统接口
```

例如：

```text
本体动作：暂停运输任务
系统能力：运输调度系统.暂停任务接口
```

动作执行映射负责完成语义参数和物理接口参数之间的转换：

```text
动作参数 reason         → 请求体 suspendReason
任务对象 business_key   → 请求体 taskId
响应 data.status        → 动作执行状态
响应 data.updatedAt     → 运输任务.lastUpdatedAt
```

完整执行流程：

1. 智能体或用户提出动作。
2. 校验目标对象状态和动作参数。
3. 执行提交条件。
4. 校验当前用户权限。
5. 必要时发起确认或审批。
6. 根据动作执行映射找到系统能力。
7. 执行网关注入凭据、追踪ID和幂等键。
8. 调用真实接口。
9. 根据成功条件验证结果，不能只依赖HTTP 200。
10. 回读或回写对象状态。
11. 失败时重试、补偿或转人工。
12. 记录完整执行审计。

当前原型已经具备系统能力、服务引用、操作名称、协议、超时、凭据策略、动作执行映射、参数映射、结果映射、成功条件和失败策略等配置入口。

但当前智能体页面执行的仍然是“演示执行”，不会调用生产接口。研发生产化还需要补充：

- 业务系统和连接器登记；
- 不同环境的连接配置；
- 请求和响应结构；
- 凭据中心引用；
- 接口连通测试和模拟执行；
- 统一动作执行网关；
- 权限、确认和审批；
- 幂等、重试、熔断、补偿；
- 执行结果验证、对象回写和审计。

## 二、下一版改造优先级

### P0：必须修改

1. 拆分本体发布状态、资源使用状态、实例业务状态和演示标记。
2. 删除资源状态中的“示例”，将“核心推荐”改为独立标签。
3. 明确动作条件默认 AND，并提供结构化条件组和确定性执行器。
4. 将“来源字段”从通用属性编辑器移除，集中到数据映射层。
5. 为动作参数建立专用数据结构和编辑器。
6. 完整定义动作、系统能力、执行映射和执行网关之间的契约。

### P1：建议一期完善

1. 删除或重构当前混合维度的对象分类。
2. 在模型图谱增加业务域、主题域筛选、高亮和隔离模式。
3. 补充关系属性的使用说明、关系实例编辑和关系属性映射。
4. 所有级联弃用操作先展示影响，再生成可审核的变更记录。

### P2：生产化建设

1. 系统能力连接器和真实接口测试。
2. 动作权限、审批、幂等、重试、补偿和执行审计。
3. 规则语言、条件执行器和规则测试集。
4. 对象、关系和动作的消费者影响分析及版本兼容治理。

## 三、核心设计原则

1. 本体定义稳定业务语义，不直接承载任意SQL、接口地址或底层字段细节。
2. 物理数据来源统一由数据映射层管理。
3. 动作是业务操作契约，系统能力才是实际接口能力。
4. 确定性判断由规则引擎或函数执行，大模型负责理解、规划和解释。
5. 所有生产写操作必须经过参数校验、条件判断、权限、确认/审批、执行验证和审计。
6. 图谱是对象和关系的派生视图，不是另一套独立事实来源。
