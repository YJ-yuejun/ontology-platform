# v1.8 会议决策与数据模型

本文是本轮原型改造的研发约束。发生表述冲突时，以会议后研发记录为准。

## 1. 最终概念结构

```text
本体容器 Ontology
└─ 业务域 Business Domain
   └─ 主题域 Subject Domain
      └─ 对象类型组 Object Type Group
         └─ 对象类型 Object Type
            ├─ 业务对象 business_object
            └─ 抽象类型 abstract_type
```

- 新确认的三个上层实体是本体容器、业务域、主题域。现有 `ontologies` 已承担本体容器职责，因此新增物理表只有 `business_domains` 和 `subject_domains`，不能再建一张同义“本体表”。
- 对象类型组保留，并下挂在主题域；它只负责分类、检索和导航。
- 业务场景描述触发、参与对象、关系路径、规则、动作和输出，可横跨多个业务域，不纳入上述树形分类。
- 共享属性是本体内可复用的属性定义，不存在“共享属性域”，也不与对象类型组建立绑定。

## 2. 接口与继承

### 2.1 物理模型

`object_types` 增加：

| 字段 | 说明 |
|---|---|
| `object_kind` | `business_object` 或 `abstract_type` |
| `parent_type_id` | 同一本体内父级抽象类型 ID；一期采用单父类 |

历史 `interfaces` 表保留但不再接受新写入。初始化时将历史接口迁移成 `abstract_type`；历史 `interface_ids` 的第一个引用迁移为 `parent_type_id`。旧接口 API 是兼容适配层，内部仍操作 `object_types`。

### 2.2 运行规则

- 抽象类型可定义属性和 Action，但不能绑定实例数据源，不能创建实例。
- 父类必须是同一本体内的抽象类型。
- 子类的有效属性 = 祖先有效属性 + 本地属性；同名属性只允许同数据类型覆盖。
- 继承在查询时递归解析，不复制属性。父类变化后，子类无需同步写入即可获得新定义。
- 创建和修改时检测循环继承；删除父类时如仍有子类则阻断。
- 业务对象必须在有效属性中恰好有一个主键；主键可以来自父类。

## 3. 审计与版本

不将变更日志和版本记录合表：

| 事实 | 表 | 粒度 | 是否可变 |
|---|---|---|---|
| 工作状态变更 | `change_log` | 单个资源的一次操作 | 发布前通过 `pending` 管理 |
| 正式版本 | `ontology_releases` | 一次发布聚合的全部变更 | 不可变 |

`change_log` 统一保存 `before_data`、`after_data`、`change_note`、操作人和时间。资源表只保留 `created_by`、`updated_by`、`created_at`、`updated_at`，不重复保存“修改说明”。

`ontology_releases` 是版本事实唯一来源。历史 `/enterprise/versions` 只读映射到发布记录；创建、修改或删除该兼容资源会被拒绝。遗留 `enterprise_versions` 表不再参与业务读取。

## 4. 业务主键与引用

- 本体容器：全局 `namespace` 唯一。
- 业务域：本体内 `code` 唯一。
- 主题域：本体内 `code` 唯一，且必须引用同一本体的业务域。
- 对象类型组：本体内 `name` 唯一，引用主题域。
- 对象类型：本体内 API 名称 `name` 唯一。
- 对象实例：本体、对象类型、`business_key` 组合唯一。

原型用应用层校验引用完整性，没有强制创建 SQLite 物理外键；生产实现必须在事务、并发写入和删除策略上提供同等或更强保证。

## 5. 页面与接口变化

- 新增“业务域与主题域”页面，可维护两级分类并查看下属对象类型组数量。
- 对象类型页用“业务对象 / 抽象类型”页签统一维护；旧“模型接口”页面和菜单退出主路径。
- 对象类型创建向导增加父级抽象类型；详情区同时展示本地、继承和有效属性/Action。
- 对象类型组创建时选择主题域，列表和详情展示业务域/主题域完整归属。
- 模型图谱展示抽象类型和继承边；抽象类型与业务对象使用不同视觉语义。
- 治理页统一展示变更日志、评审状态和不可变发布版本。

主要新增接口：

```text
GET/POST  /api/ontologies/{ontologyId}/business-domains
PUT/DELETE /api/business-domains/{id}
GET/POST  /api/ontologies/{ontologyId}/subject-domains
PUT/DELETE /api/subject-domains/{id}
GET       /api/object-types/{id}/inheritance
```

对象类型列表可使用 `include_abstract=false` 只返回可实例化业务对象。

## 6. 与 Foundry 理念的边界

本实现保持 Foundry 风格的 Object、Property、Link、Action、Interface 契约、Working State、Review 和 Release 思路。业务域/主题域是结合国内企业数据治理实践增加的目录层；把 Interface 与 Object Type 合并是存储实现选择。产品语义上仍明确区分业务对象与不可实例化的抽象契约，避免为了少一张表而丢失 Interface 的作用。
