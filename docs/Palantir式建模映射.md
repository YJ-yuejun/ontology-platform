# Palantir Foundry 式建模与本原型的映射

本项目借鉴 Foundry Ontology 的核心思想：以对象类型、属性、关系类型、接口、Action、函数、数据映射和权限构成可运行的企业语义层。它不是 Palantir 产品的复制品，也不会为了“像 Palantir”而加入当前业务没有明确价值的概念。

## 核心映射

| Foundry 式概念 | 本原型 | 说明 |
|---|---|---|
| Ontology | 本体 | 独立命名空间、治理和发布边界 |
| Object type | 对象类型 | 业务实体、事件、单据和工作项的稳定契约 |
| Property | 对象属性 | 主键、标题、状态和业务字段 |
| Link type | 关系类型 | 有方向、有基数的对象间业务事实 |
| Interface | 接口 | 独立契约资源；对象显式实现接口属性 |
| Action type | 动作类型 | 允许对对象执行的业务操作及参数、前置条件 |
| Function / Logic | 规则与函数 | 确定性计算、校验和查询逻辑 |
| Data backing / Mapping | 数据源与映射 | 物理数据到对象、属性和关系的稳定绑定 |
| Object instance | 对象实例 | 运行期真实业务记录 |
| Security | 权限策略 | 约束可见、修改和动作执行 |
| Working state / Release | 工作状态与发布版本 | 变更评审后形成不可变版本快照 |

## 企业治理扩展

业务域和主题域是本项目为企业数据治理增加的分类维度：

```text
本体 → 业务域 → 主题域 → 对象类型
```

它们不是运行时继承关系，也不改变对象类型的属性和行为。业务场景与这条树正交，可以跨越多个业务域或主题域。

本版本不提供对象类型组和共享属性：

- 对象类型组与业务域、主题域重复，已经移除；
- 共享属性的复用诉求先由接口契约承接，已经移除；
- 接口保持独立，不与对象类型或“抽象对象”合并。

这不违背 Foundry 的核心逻辑。Foundry 的价值不在于堆齐概念名称，而在于形成稳定的对象语义、可治理数据映射、明确的行为契约和安全运行边界。

## 建模顺序

1. 先从真实业务场景和决策问题出发，而不是从数据库表开始。
2. 识别稳定对象及其身份主键、标题和状态。
3. 建立对象关系并明确方向、基数和业务成立条件。
4. 登记权威数据源，分别建立对象、属性和关系映射。
5. 对跨对象通用契约按需定义接口。
6. 把确定性判断建成规则/函数，把受控业务操作建成 Action。
7. 用真实实例验证对象链路、规则结果和动作输入。
8. 将资源组装为业务场景，明确触发、角色、输出和验收口径。
9. 经过工作状态、校验、评审和版本发布后，才允许应用与 Agent 使用。

## 接口与继承

接口表达“对象必须具备什么”，不是“对象是什么”。例如“可审计接口”要求对象具有审计状态和处理人，但它本身不产生实例。

v1.9 的实现方式：

- 接口独立存储和维护；
- 对象可实现多个接口；
- 接口属性在对象上显式存在，便于查询、映射和版本 Diff；
- 保存与发布均校验属性名称和类型；
- 接口被引用时禁止删除。

对象父类继承不在当前范围内。它与接口不是同一概念，未来若实现必须单独解决属性冲突、多继承、Action 继承、数据映射和版本兼容问题。

## 多本体与图谱

默认一次编辑一个本体，图谱也展示当前本体的对象和关系。这符合以安全、生命周期、团队协作和发布为边界进行治理的方式。

跨本体全局视图可以作为二期的“企业语义地图”，但应只展示受治理的引用、共享标识和依赖关系，不能把不同权限边界的全部对象实例直接拼成一张无边界大图。

## Agent 交互

Agent 不应直连数据库自由查询或写入。推荐工具层次：

```text
对象检索 → 关系穿透 → 规则/函数执行 → Action 提案
                                     → 权限校验/人工确认 → 执行网关
```

LLM 负责意图识别、查询规划、语义抽取和解释；对象查询、关系遍历、规则计算、权限与 Action 执行由确定性服务完成。所有生产 Action 都应具备审批、幂等、超时、重试、补偿和审计。
