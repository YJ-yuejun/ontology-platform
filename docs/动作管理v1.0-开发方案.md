# 动作管理 v1.0 开发方案

日期：2026-10-29。依据：研发提供的 `ont_action` 表结构，以及当前 `/ontology/model/actions` 原型源码。

原型实现已于 2026-10-29 完成，详见 [动作管理 v1.0 PRD](prd/12-PRD-动作管理v1.0.md)。本文保留原始开发方案口径；实际范围与验收以 PRD 为准。沿用此前本体动作建模方法，但将实施范围收敛为定义管理；此前《动作模块-Palantir调研与系统设计》作为后续运行能力的参考，不作为本版验收范围。

## 1. 评估结论与版本范围

**这张表可以先用。** 它已覆盖动作基础信息、对象关联、参数、条件、处理说明、结果、审批标记和维护信息，能够支撑动作定义的增删改查，以及简单对象操作、公式、API 的登记。

建议先完成少量表约束修正和原型补齐，不新建动作执行平台，不要求多对象事务、自动规则引擎或完整审批系统。

| v1.0 做什么 | 交付行为 |
|---|---|
| 动作建档 | 在当前本体下新建动作，设置行动编号、名称、API 名称、类别和作用对象 |
| 查询维护 | 列表、搜索、筛选、分页、详情、编辑、受引用保护的删除 |
| 简单操作定义 | 选择创建/修改/删除等操作，文字填写属性变化与处理逻辑 |
| 文字规则 | 填写业务前置条件、执行步骤、预期结果与联动说明 |
| 公式定义 | 填写公式、变量说明与样例，完整保存并展示 |
| API 定义 | 填写请求方法、接口地址、参数映射、返回说明与成功条件 |
| 参数与结果 | 维护基本参数列表；可选填写结果结构 JSON |
| 维护与留痕 | 责任人、建模状态、版本信息、创建修改信息、变更记录 |

本版的“可用”指**能够完整管理动作定义**。保存公式不计算结果，保存 API 不发起调用，选择 modify 不直接修改对象实例；“需审批”表示未来执行要求，不触发审批流。页面不设置“运行成功”“测试通过”这类会误导用户的结果。

## 2. 表结构最小修正

### 2.1 建议落库前完成

| 项目 | 处理建议 | 原因 |
|---|---|---|
| API 名称唯一 | 新增 `UX_OACT_API_NAME = (oact_api_name, oact_ontology_id)`；新建必填 | 当前方案只有行动编号和中文名唯一，API 引用也需要稳定唯一 |
| 关键必填 | 明确 act_id、act_name、act_type、tgt_obj、api_name、ontology_id、status 为 NOT NULL | 避免空值绕过唯一约束或出现无归属记录 |
| 对象/属性变化关联 | 删除 `oact_obj_attr_chg → ont_obj_prop` 外键标注；保留 varchar(255) 文字说明 | 这个字段可能表达多个属性的变化，不是一个属性 ID，也不具备外键类型 |
| 行动类型 | `oact_act_type` 存 dic_action_type.code，页面展示字典名称 | 例如存 business，展示“业务行动”；名称调整不影响引用 |
| 动作规则 | 建议中文标题改为“对象操作”，枚举补齐 invoke | modify/create 等是对象操作类别；纯通知、公式、人工处置可用 invoke（不直接声明对象增删改） |
| 是否需审批 | INT 保留，限定 0/1，NOT NULL DEFAULT 0 | 明确 1=需审批、0=不需要，接口用 boolean；不接受其他整数 |
| 所属本体 | NOT NULL，作为普通关联列参与联合唯一索引 | 表中标为 UK 不代表 ontology_id 单列唯一，一个本体可以有多个动作 |

记录主键 `oact_id` 的 int 自增方案可用。`oact_act_id` 是业务编号，不与记录主键混用。三个唯一约束均为**同本体内**唯一，不建立 act_id、act_name、api_name 单列全局唯一约束。

API 名称建议沿用原型格式 `^[a-z][a-z0-9_]*$`，最长 100，例如 `assign_work_order`。行动编号最长 80，不强制只支持 A-001；编号与 API 名称创建后只读，中文名可改。字符串去首尾空格，唯一比较遵循明确的数据库排序规则；API 名称采用小写规范，避免大小写歧义。

若研发暂时不能为对象操作增加 invoke，可先允许对象操作为空，界面显示“不直接变更对象”，且原型适配为 invoke；不能把纯通知或计算默认写成 modify。推荐直接统一枚举为 `invoke/create/modify/create_or_modify/delete`。

### 2.2 当前字段可以保留的部分

- `oact_pre_cond`、`oact_exec_logic`、`oact_obj_attr_chg`、`oact_exec_result`、`oact_side_effect` 都可先作为描述保存。
- `oact_input_params` 用 JSON 数组；`oact_result_schema` 用 JSON 对象；后端解析校验后再序列化存 LONGTEXT。
- `oact_description` 表达“为什么需要这个动作”，`oact_exec_logic` 表达“怎样处理”，两者分别维护。
- `oact_status` 只表达 TemplateModelingStatus，不表达执行成功、启用权限或发布状态。
- `oact_ver` 为动作定义版本信息，不代表存在独立的历史版本表或运行版本隔离。
- 创建修改信息由服务端填写；不开放用户编辑。

所有长度限制前后端一致，超长返回字段错误，不截断保存。复杂公式、API 请求样例放 LONGTEXT 或扩展字段，不挤入 255 字段。

### 2.3 应用层关联校验

不建库级外键可以沿用，但写入时必须检查：本体存在且可编辑、目标对象存在且属于当前本体、字典 code 合法。对象和字典删除时反向检查动作引用。

如果允许并发删除对象与创建动作，关联检查与写入必须纳入一致的事务/资源锁策略，避免检查后对象已删除。动作删除还需检查场景、执行映射及其他已登记消费者引用。

## 3. 与当前原型逐项对照

当前 CRUD 已存在，主要修改表单、保存映射和后端校验，无需重建整个页面。

| 研发字段 | 当前原型字段/行为 | v1.0 改法 |
|---|---|---|
| oact_id | id，UUID | 原型继续 UUID；正式后端用 int。API 将其视为不透明记录标识，不做数值推导 |
| oact_act_id | external_id；行动ID输入框 | 保留，补后端同本体唯一与不可改校验 |
| oact_act_name | display_name；行动名称 | 保留，补后端同本体唯一 |
| oact_act_type | action_category；目前按中文名称保存 | 改为 code 保存、名称展示，兼容历史中文值 |
| oact_tgt_obj | target_object_type_id；目前按显示名匹配 | 改为真正的对象 ID 下拉选择；保留原始作用对象备注 |
| oact_input_params | parameters；文本按标点拆分为 param1 等 | 改为轻量参数行编辑，防止重排/改名造成 key 变化；保留旧参数定义 |
| oact_pre_cond | precondition_text / preconditions | 前置条件文字框，允许填写公式文本；不合并覆盖旧结构化条件 |
| oact_exec_logic | execution_logic | 保留文字编辑，支持按填写形式显示对应提示与扩展信息 |
| oact_obj_attr_chg | object_effect | 保留文字说明，不作为属性 ID |
| oact_exec_result | result_text | 改标题为“预期执行结果”，与实际执行结果区分 |
| oact_side_effect | side_effects_text / side_effects | 保留全文，不再按逗号自动拆解长句 |
| oact_need_appr | approval_required | 保留开关，提示为执行审批要求标记 |
| oact_owner | owner | 保留文本输入 |
| oact_status | design_status；当前存中文或英文混用 | 接 TemplateModelingStatus 统一代码，页面显示中文 |
| oact_ver | 当前 ActionBase 无独立版本字段，旧 metadata 可能包含来源版本 | 新建默认 v1.0；先保存在扩展元数据，详情展示 |
| oact_result_schema | result_schema；当前页面把结果文字写成 result 键 | 增加独立 JSON 编辑区，避免把结果说明冒充返回结构 |
| oact_api_name | name；新建时由编号自动拼 action_xxx | 增加显式输入，创建后只读，不随中文名/编号变化 |
| oact_action_type | action_type；支持 invoke，但页面不能选择，新建默认 invoke | 新增“对象操作”下拉，中文展示、英文存储 |
| oact_description | description；当前与 execution_logic 同步 | 增加独立业务说明，不再相互覆盖 |
| oact_ontology_id | ontology_id / activeId | 由当前本体上下文与服务端校验确定，不手填 |
| created/updated 四列 | 已有记录和变更日志，但 actor 存在固定演示值 | 展示服务端值；正式研发对接当前用户，原型标识演示身份 |
| oact_extend_params | metadata；目前没有独立可编辑的扩展契约 | 增加白名单字段适配；保留未知历史元数据，不默认渲染任意键 |

注意 `design_status` 与原型 `status=experimental/active/deprecated` 是两个维度。正式表的 oact_status 映射前者；后者暂以 `extend_params.resource_status` 兼容，继续由现有治理逻辑维护，不在本版新增一个相冲突的启用开关。

## 4. 初版页面方案

保留现有“目录列表 + 详情面板 + 编辑弹窗”，不做完整多页设计器。

### 4.1 列表与详情

工具栏：关键字（编号/名称/API 名称）、行动类型、作用对象、建模状态筛选、清空筛选、新建。

列表建议：行动名称/编号、API 名称、行动类型、作用对象、对象操作、建模状态、更新时间。参数和前置条件移到详情，减少大段文本挤占列表。

详情按基础信息、参数、操作定义、结果与联动、维护信息分组；公式、请求内容等保留换行。操作为编辑、删除、查看变更记录；已发布/被引用记录按现有治理约束处理，不直接放开删除。

### 4.2 新建/编辑弹窗

| 分组 | 字段与控件 |
|---|---|
| 基础信息 | 行动编号、中文名、API 名称、行动类型字典、作用对象下拉、业务说明 |
| 输入参数 | 参数 key、中文名、类型、必填、默认值/说明；添加/删除参数行 |
| 操作定义 | 对象操作下拉、填写形式、前置条件、执行逻辑、对象/属性变化 |
| 结果与联动 | 预期结果、副作用说明、结果结构 JSON（可选） |
| 审批与维护 | 是否需审批、责任人、建模状态；版本及审计信息只读 |

新建必填：行动编号、名称、API 名称、类别、作用对象、填写形式、执行逻辑、责任人、建模状态。文字/公式/API 模式下均填写可读的执行逻辑；公式和 API 补充自己的必填项。输入参数可以为空数组，例如无参数通知动作。

“保存到工作状态”只保存定义。可提供“检查填写”按钮做字段、引用与 JSON 格式校验，不提供执行/连通性测试按钮。

### 4.3 三种填写形式

| 填写形式 | 展示与校验 | 保存 |
|---|---|---|
| 文字规则 text | 执行逻辑多行文本，提供步骤示例；校验非空与长度 | 主要使用 oact_exec_logic |
| 公式 formula | 公式文本、变量说明、可选输入/预期输出样例；校验必填与长度，不宣称公式语法或业务正确 | 公式信息存 extend_params.formula；exec_logic 保存可读说明 |
| API api | 方法、URL/路径、请求参数映射说明、请求示例、返回映射、成功条件说明 | API 信息存 extend_params.api；exec_logic 保存处理步骤 |

填写形式是编辑方式，不决定对象操作，也不决定行动类别。例如“修改工单状态”可以采用文字规则或 API 填写；“通知行动”也可能登记一个 API。

API 首版只登记 HTTP 方法及地址/路径；路径可为 `/api/work-orders/{work_order_id}/assign`，系统名称单独备注。方法限定 GET/POST/PUT/PATCH/DELETE；地址只做基本格式和长度检查，不探测网络。GET 登记不代表可以承担真实修改操作。

请求示例与参数映射先允许普通文本，结果结构区才要求 JSON 对象。认证信息只写凭据引用/认证说明，不要求录入真实密钥。若已有“动作执行映射”，优先关联该映射并只读展示其 API 信息，避免两处维护；未关联时允许在本动作里登记简单 API 说明。

参数编辑尽量复用已有 ActionParameterEditor，隐藏当前不需要的高级来源配置。稳定 key 与中文名分开；JSON 数组由前端生成。结果结构提供小型可选文本框，能解析为对象即可，若需使用完整 JSON Schema 再单独约定方言；本版不实现 schema 推导和返回结果校验。

## 5. 扩展字段约定

推荐仅增加下列受控结构。以下示例用于研发理解，不要求业务用户编辑整段扩展 JSON。

```json
{
  "schema_version": 1,
  "definition_mode": "api",
  "resource_status": "experimental",
  "api": {
    "method": "POST",
    "url": "/work-orders/{work_order_id}/assign",
    "system_name": "工单系统",
    "request_mapping_text": "路径 work_order_id <- 参数 work_order_id；body.assignee <- 参数 assignee",
    "request_example_text": "{\"assignee\": \"u001\"}",
    "response_mapping_text": "返回工单编号、状态与处理人",
    "success_criteria_text": "业务返回码为 0 且工单状态为已分派",
    "credential_ref": ""
  },
  "formula": {
    "expression_text": "",
    "variables_text": "",
    "example_text": ""
  }
}
```

可追加 `legacy` 原文信息与已有执行映射 ID。公式模式使用相同 formula 子结构；文字模式无需填 api/formula。切换填写形式保留原配置，但详情明确只显示当前选中形式，非当前形式不被当作有效定义。

原型需要新增可被 Pydantic 接收和仓储持久化的字段，例如 `definition_config`、`definition_version`，分别写入现有 metadata；正式后端适配到 oact_extend_params 和 oact_ver。不能只在前端传字段，否则会被当前模型过滤。

扩展字段按白名单控件展示，未知键保留但不自动转为可编辑控件。更新采用服务端合并策略：显式修改的字段覆盖，未传字段保留，显式清空按契约处理；不可用整段新 JSON 静默抹掉旧模板谱系或扩展数据。

## 6. 保存、编辑、删除规则

### 6.1 保存校验

- 行动编号、中文名、API 名称在同一本体内唯一；前端提示用于体验，后端及正式库唯一索引兜底。
- 本体和作用对象一致；新建只允许有效字典 code。历史禁用值原样保留时可编辑其他字段，重新选择只能选有效项。
- 参数 key 非空、格式规范、不重复；类型与默认值兼容；枚举有选项。新增参数采用用户明确 key，不按列表位置生成身份。
- 输入参数为数组，结果结构为空或对象，扩展为对象。未知参数类型不能静默转成 string。
- 各字段长度遵守研发表定义；删除/改变参数不悄悄改掉关联文本，提示用户检查公式与 API 映射即可，不做自然语言引用解析。
- `对象操作` 和填写形式按固定枚举校验；“需审批”校验为 boolean/0/1；状态校验统一代码。

### 6.2 编辑与版本

新建动作定义版本默认 v1.0，保持只读。普通保存不自动递增独立动作版本；正式发布时由现有本体版本机制关联更新。正式后端若尚无该机制，v1.0 只保存初始版本和 updated_at，不宣称支持历史回滚。

用 expected_updated_at 做最低限度并发冲突检测；后端事务内比对，变化则返回 409 提示刷新。行动编号、API 名称创建后不允许普通编辑修改。已发布资源仍按现有工作状态机制变更。

### 6.3 删除

删除前提示动作名称；后端检查是否仍被场景、动作执行映射等引用，有引用返回阻止原因与资源清单。无引用且允许删除的草稿才能物理删除，不能级联删除关联资源。

保留原型“active 不能直接删除”的限制，并提供现有弃用/发布治理路径的跳转或说明。正式后端 oact_status 是建模状态，不能单凭“已确认”判断已发布；发布状态从本体版本及 resource_status 兼容信息判定。

## 7. 接口与代码改造

### 7.1 复用现有五个接口

| 接口 | v1.0 处理 |
|---|---|
| GET /api/ontologies/{ontology_id}/actions | 返回列表与扩展配置、版本信息；原型继续前端筛选分页即可 |
| POST /api/ontologies/{ontology_id}/actions | 增加业务编号/中文名/API 唯一、字典 code、扩展配置等校验 |
| GET /api/actions/{id} | 返回完整定义、对象名称、审计信息 |
| PUT /api/actions/{id} | 校验所属本体访问范围、稳定标识不可改、并发标记；保留未改历史字段 |
| DELETE /api/actions/{id} | 增加引用保护与当前本体访问校验，写入变更记录 |

正式后端可支持 keyword/category/object/status/page/page_size 做服务端检索；不要求为少量数据原型新增另一套分页接口。本体归属和当前用户由服务端校验，不相信前端提交的 created_by/ontology_id。

正式表名保持 ont_action；原型继续用 SQLite actions + metadata，通过字段适配验证产品交互，不为演示更换主键、重建库或覆盖现有用户数据。

| 导入、导出、复制与 Proposal | 新增定义字段跟随原动作流转，复制时重映射对象/执行映射 ID |

### 7.3 旧数据兼容

- 旧中文行动类别只有唯一匹配时才转 code；无法匹配的记录展示“历史值待规范”，不猜测覆盖。
- 作用对象保留 target_role / template_raw 原文，正式引用使用 target_object_type_id；原文“阀门”等角色不被对象类型显示名覆盖。
- 旧参数完整读取，改显示名/排序不丢 key、类型、必填等信息。
- 旧 preconditions、result_schema、side_effects 与文字字段分别保留；仅编辑业务说明时不重建这些结构。若用户修改对应文字，应明确其为说明层修改，不自动改写已有结构。
- 历史 `result_schema={result: '某段文字'}` 原样展示兼容，可由用户主动修订；不静默迁移成另一种结构。
- 正式建唯一索引前扫描并报告存量重复项，人工解决后加约束，不自动改编号/改名。

## 9. 实施顺序与验收

1. **统一字段口径**：落实三种唯一性、对象操作枚举、状态代码、扩展契约与数据适配。
2. **补后端定义管理**：保存、查询、更新、删除保护、新字段往返及日志。
3. **轻改原型页面**：保留现有布局，接入新字段、参数表格、三种填写形式与校验反馈。
4. **验证完整闭环**：三种样例从新建到搜索、详情、编辑、刷新、删除，并回归已有模板数据与导出复制。

不将运行网关、真实执行、复杂审批、事务 Outbox 等加入本版排期。

| 验收场景 | 通过标准 |
|---|---|
| 文字/公式/API 分别新建 | 必填完整可保存，刷新后所有字段一致 |
| 同本体重复编号/中文名/API | 各自被后端拒绝；另一本体允许相同业务值 |
| 选择作用对象 | 实际保存对象 ID，跨本体 ID 提交被拒绝 |
| 行动类型 | 保存 code，页面和筛选展示中文，字典在用保护正常 |
| 参数改名和排序 | key 和类型不变，不按下标重新生成 |
| 结果 JSON 错误 | 字段级提示，不保存半条记录 |
| 多行公式/API 文本 | 换行保留，中文标点不导致字段自动拆分 |
| 两人并发编辑 | 旧版本保存返回冲突，不覆盖新内容 |
| 删除 | 草稿无引用可删；有场景/映射引用或发布限制时阻止 |
| 历史动作编辑 | 仅改责任人，不丢原始参数、条件、谱系、结果结构 |
| 变更记录/对比/导出复制 | 新字段纳入记录与定义流转，引用仍正确 |
| 版本与审批 | 显示为定义版本及审批要求，没有伪造运行/审批成功状态 |

结论：保留研发这张主表，做上述约束和语义修正，再对现有原型进行轻量补齐，就能形成可交付的动作管理 v1.0。该版本以“定义完整、可维护、可追溯”为验收目标，未来执行能力继续沿同一动作标识与配置扩展。
