## 2. 版本比对：改用「复制本体分支」的可行性

### 2.1 结论

**方向可行，而且比现在的 release 快照机制更简单。** 但有两个必须先纠正的认知，否则会低估工作量：

1. **现有的导出/导入并不是"整本复制"**：它给所有资源生成**全新 UUID**，而且对当前两个真实内置本体 export→import **直接抛 ValidationError**（已实测）。
2. **现有 version-compare 只能在同一个本体内部对比**（release 快照 vs working），跨本体对比必须新写；且它的匹配键是 UUID，跨本体 naive diff 会把**所有资源同时报成新增和删除**。

### 2.2 现在的版本对比在做什么

- 机制：**发布时存快照，对比时对快照做纯 JSON 语义 diff**，不是实时库对比。发布把 `_current_semantic_snapshot()` 写进 `ontology_releases.snapshot`（`backend/repository.py:1467, 1482-1485`）；对比时 `_snapshot_for()` 的 SQL 带 `WHERE ontology_id=?`（`backend/governance_insights.py:253-263`）——**同本体限定**。
- 覆盖 15 类资源（`governance_insights.py:18-34`）：8 类按白名单字段比（`:35-46`），7 类全字段比（`:103-105`）。**显式不含实例**。
- 匹配键 `_semantic_index`（`:96`）：非企业资源用 UUID 优先，企业资源用 `code` 优先。
- 同一快照机制还被三处复用：只读历史版页、数据映射的"图谱版本"下拉、质检指纹。**这三处是会连带受影响的隐藏依赖。**

### 2.3 现有 import 为什么跑不通（实测）

`import_ontology`（`repository.py:1843-1892`）的资源顺序是：

```
本体 → 业务域 → 主题域 → 接口 → 对象类型 → 关系 → 动作 → 规则 → 实例 → enterprise 资源(最后)
```

问题：

- **对象类型（`:1860-1869`）先于数据源（`:1880-1891`）导入**，而 `_validate_backing_source`（`repository.py:705-709`）要求数据源已存在 → 带 `backing_source` 的对象类型必失败。采购与财务本体即因此报"映射数据源必须选择当前本体已登记的数据源"。
- 主题域校验（`repository.py:719-728`）要求 `subject.business_domain_name == data.domain`，而模板遗留的 `metadata.domain` 是旧业务域 → 管网本体报"主题域必须属于对象选择的业务域"。

另外 **`tests/test_api.py` 里没有任何 import/export 用例**，这条路径长期无覆盖。

**不会复制**的东西：`ontology_releases`、`ontology_quality_runs`、`change_log`、`proposals`、`build_runs/sessions`、`scenario_runs`、`agent_interactions`、数据源密码、`source_schema_snapshots`、`evidence_sources`、`template_records`（后两者 export 里有、import 完全没消费）。

### 2.4 跨本体 diff 的关键技术前提：稳定键（最重要）

复制分支后所有资源都是新 UUID，所以**必须用业务稳定键做匹配**。可用的键（schema 均有 `UNIQUE(ontology_id, X)`）：

| 资源 | 稳定键 |
|---|---|
| `object_types` / `interfaces` / `link_types` / `actions` / `business_rules` | `name` |
| `business_domains` / `subject_domains` | `code` |
| 8 类 enterprise 资源（含 governance-assets） | `code` |

⚠️ **`external_id` / `template_external_id` 不能当匹配键**：对象/关系/动作的它塞在 `metadata` JSON 里而非独立列，且填充率很低（对象 10/23、关系 10/28、动作 4/14、治理资产 0/7）。只能作展示证据。

另一个必做动作：**比较前要把 `subject_domain_id` / `business_domain_id` / `source_object_type_id` / `target_object_type_id` / `interface_ids` 从 UUID 归一化成对侧稳定键**，否则跨本体对比时每个对象、每条关系都会被报成"已修改"。

### 2.5 会连带破坏的东西（迁移清单）

- **DB**：`ontology_releases`；`ontologies.version / based_on_version / status` 三列；`mdl_ver_chg` 的投影触发器（发布时归档）。
- **API**：`/releases`、`/releases/{rid}/snapshot`、`/release-preview`、`/publish`、`/derive`、`/review/submit`、`/review/approve`、`/version-compare[/chat]`。
- **前端**：`App.jsx` 导航与路由（`:72-73, 98, 261, 263`）、整页 `VersionCompare.jsx`、整页 `ReleaseSnapshot.jsx`、`Governance.jsx`、以及 `DataMappingStudio.jsx` 的「图谱版本」下拉（`:96-98, 128, 153-159, 332`）。
- **状态机**：四态校验与 `_log` 强制回退 draft（`repository.py:491-498, 1377-1412, 1443-1504`）、内置本体的 seal/backfill 造 release（`enterprise.py:2732-2788`）、versions 统计（`enterprise.py:219-224, 801`）、质检的 `version_label` 依赖（`governance_insights.py:214-215`）。
- **测试**：5 处以上依赖 publish/release，需要重写。

**必须保留（审计用途，不能跟着一起删）**：`change_log` + `mdl_ver_chg`、`ontology_quality_runs`、proposal / build session。

### 2.6 建议的最小可行设计

1. `ontologies` 加 `origin_ontology_id`（用现成的 `_ensure_column` 迁移，参考 `repository.py:324`），副本命名 `原名_copy` / `原名v2`。
2. 新写 `copy_ontology()`——**不要复用现有 import**，按 FK/校验安全顺序重写：本体 → 业务域 → 主题域 → **数据源 + 治理资产先于对象类型** → 接口 → 对象类型（清空/改写 `metadata.domain` 以避开两级域校验）→ 关系 → 动作 → 规则 → 其余 enterprise 资源 → 实例。保留 `name`/`code`/`external_id`；不复制 releases / change_log / quality / proposals / 密码。
3. 新写 `compare_ontologies(a, b)`：复用现有 `SECTIONS` / `SEMANTIC_FIELDS` / `_clean()`，但**索引键换成上面的稳定键 + 引用 UUID 归一化**。端点如 `GET /api/ontologies/{id}/diff-with/{other_id}`，前端改成"选两个本体 → 出报告"。
4. release 机制（UI / 端点 / 表）可整体删除。

**一句话**：这个减法做得对，但要落两块新代码（深拷贝 + 稳定键 diff），不是"把发布按钮删掉"那么简单。

## 3. 字典管理：优化清单

### 3.1 现状（能用，但契约不干净）

- **两套字典体系并存**：`/api/dictionaries*` 只读（8 类 37 行，`ontology_dictionary_items`）与 `/api/model-dictionaries*` 完整 CRUD（V4 7 表，44 行）。同码不同名：`string`=文本 vs 字符串、`rest`=REST API vs REST、`file`=文件交换 vs 文件。
- 「在用项不可禁用或删除」确实是**服务端硬阻断 409**（`backend/dictionary_service.py:184-187, 213-214`），但 UI **不显示引用数、不做预检**，用户必须点保存吃到 409 才知道原因。
- 「在用」判定 `_references`（`:97-125`）只做 **code/name 严格相等**匹配、只扫 6 个固定 JSON 位置。**不在字典里的历史值不计引用** → 相关字典项"看似无人用"可被删除，资源侧自由文本永久留存，字典永远收敛不了。

### 3.2 实测到的数据契约问题

| 问题 | 实测证据 |
|---|---|
| **同一字段混装 code 与 name** | `enterprise_data_mappings.payload.map_way`：`direct`×3（code，system-migration 写入）与 `直接映射`×6（name，UI 写入）并存；另有 `关联映射`×2、`字段/单位映射`×3、`枚举映射`×3 |
| **重选一次就把 code 改写成 name** | `DictionaryField.jsx:116, 119-121` 的值槽同时接受 code/name，`onChange` 一律回写 name → 用户在下拉里重选同一个可见项，`direct` 就静默变成 `直接映射` |
| **转换规则 0 命中** | `transform_rule` 与 `dic_xform_rule` 的 code/name **匹配 0 行**（实际值：待按企业口径确认×10、-×2、统一MPa×1、源值→标准状态×1） |

### 4.3 根因

`.mapping-graph-canvas` 是 `flex: 1` + `min-height: 460px`（`frontend/src/styles.css:1949`），它的父级 `.mapping-graph-main` 是**自动高度的 grid 行**（`:1947`），而 vis-network 注入的子元素 `.vis-network` 是 `height: 100%`。于是形成**循环尺寸依赖**：容器高度 ← 子元素内容高度 ← 容器的 100%。

叠上 vis-network 的 `autoResize: true`（`MappingLineageGraph.jsx:29`），ResizeObserver 每次观察到尺寸变化就重设画布 → 容器再变高 → 无限增长，同时渲染始终无法稳定完成，所以画不出任何节点。

**对照实验（决定性证据）**：隔壁的「模型图谱」用同一套 vis-network，但 CSS 是 `.network-canvas { flex: 1; min-height: 0 }` + `.graph-layout { overflow: hidden }`（`styles.css:144`），实测 **510px 恒定不变，图形正常**。两者唯一差别就是这个高度约束。

**运行时 CSS 注入验证**：

| 实验 | 结果 |
|---|---|
| 原样 | 987 → 1350（仍在涨）❌ |
| A：`.mapping-graph-canvas { flex: none; height: 520px }` | 520 → 520 稳定 ✅ |
| B：`.mapping-graph-main { height: 100%; min-height: 0; overflow: hidden }` + `.mapping-graph-canvas { min-height: 0 }` | 542 → 542 稳定 ✅，**节点与连线正常显示** |

### 4.4 修复方案（建议用 B，改动最小）

```css
/* frontend/src/styles.css 约 1946-1957 行 */
.mapping-graph-layout { overflow: hidden; }                        /* 新增 */
.mapping-graph-main   { height: 100%; min-height: 0; overflow: hidden; }  /* 新增前两行 */
.mapping-graph-canvas { min-height: 0; }                           /* 460px → 0，改由外层 min-height:540px 兜底 */

/* @media (max-width: 980px) 分支里 height:auto，需保留画布最小高度 */
@media (max-width: 980px) { .mapping-graph-canvas { min-height: 520px; } }
```

### 4.5 对 AI 提出的三层血缘方案的评估

**总体：方案合理、方向与已定架构一致，但现状几乎全部没有实现，且方案本身漏了两点。**

| AI 方案要点 | 现状 | 结论 |
|---|---|---|
| 默认按表/接口、治理实体、本体类型**聚合**展示 | 现在是**字段级平铺**：`DEMO-GA-TASK → TransportTask` 因 3 个属性映射画了 3 条边 | **未实现**，需新增聚合层 |
| 点击节点再**展开字段级**映射，避免一打开几百条线 | 无下钻，点节点只显示「层级 + 标识」 | **未实现** |
| 点击连线右侧显示映射详情，**沿用模板字段** | 有 `selectEdge`，但详情只有「连线类型 + 依据」两项，不显示来源系统/来源表/来源字段/映射方式/转换规则/质量校验/更新方式/负责人 | **部分实现** |
| 按业务域、主题域、数据源、治理资产、本体对象**筛选** | 只有一个单选的「查看范围」下拉；**没有业务域/主题域筛选** | **部分实现** |
| 查看某节点的**上游、下游和相关路径** | 无 | **未实现** |
| 切换版本后图谱读取对应版本配置 | **已实现**（图谱版本下拉 + release snapshot） | 已实现，但会随版本机制简化一起被删 |
| 缺失节点、失效引用**清楚标识，不能静默隐藏** | `buildMappingLineage` 有三处静默 `return`：`!semanticCode`（`:17`）、`!asset`（`:22`）、`!source`（`:38`）→ 映射直接消失，连计数都没有 | **未实现，且与要求相反** |
| 未提供物理层血缘时只展示「治理资产 → 本体」，**注明上游信息未提供** | 缺上游时确实不画物理节点，但**没有任何"上游未提供"的标识** | **部分实现** |
| 物理→治理**支持一条资产多条上游** | `asset.upstream_source_code` / `upstream_object` 是**单值字段**，且边 id 写死 `upstream:${asset.id}` 去重 → 一个资产**只能有一条上游边** | **未实现，是数据模型限制**（用户自己的担心成立） |

**方案漏掉的两点，建议补上：**

1. **聚合/下钻要有明确的交互出口**：现在是"一打开就是字段级"，改成聚合后必须同时给出"展开到字段"和"收起"的显式操作，否则排查问题时反而更难定位。
2. **静默丢弃必须改成显式告警**：至少要有一个"未能上图的映射 N 条 + 原因"的提示条。当前 `buildMappingLineage` 连 `console.warn` 都没有，是隐形故障。

**关于"造数据"**：管网本体**已经有** 7 个 `DEMO-GA-*` 治理资产 + 10 条 `DEMO-MAP-*` 映射（由 `backend/seed_pipeline_mapping_demo.py` 播种，payload 带 `demo_marker`，状态为 `example`），三层链路是完整的。采购与财务本体则只有 3 条旧版直连映射、0 个治理资产。另外 `source_schema_snapshots` **全库 0 行**——也就是说物理层节点目前只来自资产 payload 里的单值 `upstream_source_code`/`upstream_object`，**没有任何真实采集的表结构支撑**。所以真正要补的不是"多一点演示数据"，而是**底层支持一条资产多条上游**这件事。
