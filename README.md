# 企业本体 Studio（高保真原型 v1.10 · 模板适配版）

> 基于原“本体技能开发”平台框架持续演进，没有重启另一套 UI。当前版本用于评审企业本体的产品逻辑、数据契约、治理流程、智能构建和 Agent 接入方式。

默认访问地址：<http://127.0.0.1:8021>。

## 1. 当前产品口径

本体不是一张知识图谱，而是位于业务数据与应用、Agent 之间的企业业务语义层：

```text
本体容器
  ├─ 业务域
  │    └─ 主题域
  │          └─ 对象类型 ─ 属性
  ├─ 接口 ─ 对象实现的结构契约
  ├─ 关系类型 ─ 对象之间的业务事实
  ├─ 数据源 / 属性映射 / 关系映射（对象主键通过属性映射表达）
  ├─ 对象实例 / 实例关系
  ├─ 业务规则 / 函数 / Action / 系统能力 / 执行映射
  └─ 场景 / 权限 / 工作状态 / 版本 / 审计
```

v1.9 已执行以下明确决策：

- 分类主路径固定为“本体 → 业务域 → 主题域 → 对象类型”。
- 删除产品中的“对象类型组”，避免与业务域、主题域重复分类。
- 删除产品中的“共享属性”，属性在对象或接口内显式定义。
- “接口”保留为独立资源，不与对象类型合并，也不使用“抽象对象”伪装接口。
- 对象可选择实现一个或多个接口；必须显式满足接口属性契约，保存和发布时都会校验。
- 对象创建不再填写“复数显示名称”。该字段主要服务英文界面的单复数文案，例如 `Contract / Contracts`；中文产品价值很低，数据库只保留为空的历史兼容列。
- 对象的“映射数据源”从已登记数据源中选择；表、字段和关系的具体绑定在“数据源与映射”页面维护。
- 业务场景不是分类标签，而是可验证的横向业务闭环：通过已治理的数据映射推导数据源，并将对象定位、关系穿透、映射读取、规则执行、动作建议、人工审批和结果验证组装为可编排步骤。
- 用户不直接编辑 JSON。可变键值结构使用表格式编辑器；枚举、资源引用和映射目标使用选择器。
- 三期发布主线为“工作状态变更 → 本体质检 → 提交评审 → 评审通过 → 发布不可变语义快照”。不能绕过质检和评审直接发布；当前只支持一个工作状态，并非完整的多分支协作系统。

V4 字典与变更记录适配：

- “语义模型 → 字典管理”统一管理 7 张全局字典：数据类型、系统类型、数据类别、接口方式、映射方式、行动类型、转换规则。业务域与主题域仍是本体目录实体，不放入该菜单。
- 数据源、属性、映射、行动等实际下拉处可就地打开对应字典的增删改查；在用项不可禁用或删除。旧原型按名称保存的值继续展示，迁移到正式 V4 服务时需要改为按 code 引用。
- “本体工作台 → 变更记录”读取 `mdl_ver_chg`，只展示时间、操作对象、操作内容和操作人，支持搜索与分页。旧 `change_log` 通过本地兼容投影保留历史，不丢用户操作。
- “本体质检”独立生成并保存当前语义层报告，检查对象、关系、接口、规则以及已配置映射/逻辑的引用；报告标识模型变更后的过期状态，不将实例或生产接口运行情况冒充为已验证。
- “本体版本对比”基于发布时的不可变快照对比语义字段，左右查看新增、修改和删除；历史版本不被编辑。两页的对话只解释已生成的报告/差异。默认使用本地规则解读，只有明确设置 `ONTOLOGY_GOVERNANCE_AI_ENABLED=1` 且配置模型密钥才会将相应证据发送到模型服务。
- 发布记录可打开只读历史语义快照；映射图谱可切换当前工作状态与历史发布版。正式快照不包含实例数据或连接密码；删除的模型资源在旧版仍保留。
- 三期重点业务逻辑、菜单和验收口径见 [三期本体治理迭代PRD.html](docs/三期本体治理迭代PRD.html)。
- V4 `dic_xform_rule` 已可管理，但原型的“转换规则”目前承载自由文本逻辑；在 `dxr_code` 的资源字段契约明确前，不把该字段强改为字典下拉。模板关系映射使用“关联映射”，而 V4 `dic_mapping_way` 尚无对应 code，因此暂保留现有值。

v1.10 在不改动模板事实字段和内置案例的前提下完成 P0/P1 前端适配：

- 资源使用状态与模板“建模状态（已确认/设计中）”分开展示；“示例”不再作为新资源状态。
- 对象类型创建按“身份 → 业务分类 → 属性结构 → 接口与映射”四步操作，保留模板对象 ID、对象类别、业务域、生命周期、负责人、来源系统和核心/事件/需行动字段。
- 属性编辑器保留模板中的属性类别、数据类型、单位/枚举、业务定义、来源系统、来源字段、更新频率、转换规则和质量要求；来源字段仍是模板字段，但正式物理绑定仍在数据映射层完成。
- 关系编辑器补齐模板关系 ID、方向、基数、来源系统、起点键、终点键、核心关系和双向展示；关系属性保留为高级配置。
- Action 使用专用参数编辑器；提交条件明确“全部满足（AND）/任一满足（OR）”，只允许受限表达式与结构化字段，不把 SQL 或接口地址写入 Action。
- 模型图谱支持业务域、主题域联动筛选、高亮/隔离和跨域关系统计。

历史包兼容说明：旧数据库中的分组、共享属性、抽象类型会在启动时迁移或清理；旧字段和兼容表不是 v1.9 产品资源，不提供菜单或 API。

## 2. 内置本体

系统只保留两个有业务价值的内置本体：

| 本体 | 作用 | 当前基线 |
|---|---|---|
| 采购与财务协同本体 | 贯通组织、项目、预算、采购、合同、验收、发票、付款、凭证与复核 | 13 个对象、18 个关系、8 条规则、10 个动作、13 个实例，`v1.0.0` |
| 管道运输运营本体 | 按《本体建模模板.xlsx》15 个 Sheet 真实导入的管网案例 | 9 个对象、10 个关系、4 个动作、2 个场景、3 个实例，模板基线 `v1.0.0` / 平台版本 `v1.1.0` |

管网本体是受保护的产品基线。启动迁移只执行一次，后续正常编辑不会被种子数据覆盖；自动化测试会检查对象、关系、Action、场景、数据源、映射、能力、权限和模板证据，防止未来修改时再次丢失。

管网对象：客户、合同、运输任务、管线、管段、站场、设备、告警、工单。

管网核心关系：

```text
客户 ─签署→ 合同 ─生成→ 运输任务 ─通过→ 管段
                                  ├─起始于/结束于→ 站场
管线 ─包含→ 管段 ─拥有→ 设备 ─产生→ 告警
                                  ├─影响→ 运输任务
                                  └─创建→ 工单
```

管网 Action：暂停运输任务、关闭阀门、通知调度人员、创建工单。

模板接入还会将工作簿的 253 条非空原始行写入 `template_records`，通过
`GET /api/ontologies/{ontology_id}/template-records` 查看原始单元格、来源行号和规范化目标；因此页面上的平台标识变化不会丢失模板原值。

## 4. 手工建模的推荐顺序

1. 新建本体并明确命名空间和业务边界。
2. 建立业务域和主题域，例如“采购管理域 → 合同管理主题”。
3. 登记数据源，只保存连接引用和物理对象说明，不保存密码。
4. 按需定义接口，例如“可审计接口”，并定义其属性契约。
5. 创建对象类型，配置唯一主键、标题属性、主题域、接口和已登记数据源。
6. 创建关系类型，明确起点、终点、方向和基数。
7. 建立对象、属性和关系映射，使用结构化样例运行映射测试。
8. 加载或维护实例数据，检查真实关系链能否穿透。
9. 定义业务规则、Action、系统能力与动作执行映射。
10. 建立业务场景，把以上资源组装为可运行、可验收的业务闭环。
11. 运行本体质检，确认待发布变更与影响，提交评审并由评审人通过后发布新版本。

## 5. 智能构建

智能构建同时支持两类任务：

- 新建本体：从业务目标和一批文件证据生成首版本体 Proposal。
- 更新本体：锁定现有发布版本作为基线，只生成增量 Diff。

产品流程：

```text
任务定义 → 文件与数据证据 → 多轮抽取/对齐 → 资源级 Proposal
        → 人工接受/驳回 → 合并工作状态 → 本体质检
        → 提交评审 → 评审通过 → 发布新版本
```

智能化边界：

- LLM 负责术语理解、候选抽取、同义对齐和解释。
- 平台负责唯一性、引用、类型、主键、权限、状态机、版本和正式写入。
- AI 只能生成 Proposal，不能直接修改已发布本体。
- 高风险删除、主键变化、关系反转和写 Action 必须人工处理。
- 未配置模型密钥时显示“确定性演示降级”，不会伪装成模型运行。

可选模型配置：

```bash
export DEEPSEEK_API_KEY="your-key"
```

当前原型调用 `https://api.deepseek.com/v1` 的 `deepseek-v4-flash`，并请求最高推理强度。生产实现必须把模型、解析器和执行器做成可替换能力，不应把密钥写入代码、数据库或提交包。

## 6. 技术架构

后端：Python 3.9+、FastAPI、Uvicorn、Pydantic v2、SQLite `sqlite3`、可选 `httpx` 模型调用。

前端：React 18、Vite、HashRouter、原生 CSS、Lucide、vis-network。

```text
React 单页应用
  └─ /api/*
       └─ FastAPI
            ├─ repository.py  核心本体、实例、治理与发布
            ├─ enterprise.py  场景、映射、证据、Proposal 与运行演示
            ├─ models.py      请求契约与校验
            └─ SQLite         原型元数据与实例
```

SQLite + JSON 适合高保真原型，不是生产存储结论。生产化需要版本化元数据、多人协作、对象索引、关系查询、连接器、细粒度权限、Action 网关和可观测性。

## 10. 生产研发重点

- 模板导入需要 Sheet 级预检、编码解析、引用检查、错误定位、局部修复和幂等重复导入。
- Schema、Mapping、Instance 必须分层版本化，主键或关系变化需要迁移计划。
- 多本体是治理和生命周期边界，不等于所有业务域都拆成本体；跨本体引用需要明确共享标识和权限。
- Agent 只能通过已发布的对象查询、关系查询、规则函数和 Action 工具工作，并继承当前用户权限。
- Action 网关必须具备参数校验、授权、审批/确认、幂等、超时、重试、补偿和审计。
- AI Proposal 必须保存证据定位、置信度、变更理由、与基线的差异和风险等级，并持续评测接受率和正确率。
