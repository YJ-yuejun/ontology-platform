01为什么需要本体

数据库告诉程序数据存在哪里；本体告诉人和机器这些数据在业务世界中是什么、如何连接、允许做什么。

02RDF、OWL 与 SHACL：学术基础

RDF：用三元组写事实

资产 A-1001  — 位于 — 上海仓库
资产 A-1001  — 状态 — 维修中
维修工单 WO-09 — 针对 — 资产 A-1001

RDF 用“主语—谓词—宾语”表达事实；RDF Schema 提供类、实例、子类、属性、domain 和 range 等基础语义。

RDF / RDFS表达资源、三元组、类、属性与基础层级。
OWL表达等价、互斥、限制、传递性等更强语义，并支持推理。
SHACL用 Shape 验证节点和边是否满足数据类型、数量与结构约束。
开放世界与封闭世界OWL 中“没有记录”通常代表未知，不自动代表假；数据库业务校验通常把缺失必填值视为不合格。企业运营本体常吸收语义网思想，同时采用更确定的数据映射、校验、权限和版本机制。

因此 Palantir 式本体不是简单的 RDF 图，而是一套面向运营的语义与行动层。

03核心概念：从类型到真实对象

对象类型 Object Type一类业务实体、事件、交易或工作对象的定义，例如 Asset、Order。
对象 Object某个类型的具体实例，例如资产 A-1001。
属性 Property对象的特征，包含稳定 API 名称、类型、枚举、来源与状态。
关系类型 Link Type两类对象之间有业务含义的连接契约。
关系 Link两个具体对象之间的一次连接。
Action Type创建、修改、删除对象或关系的受控业务动作。

对象类型并不只是“物”

人：员工、客户地点：仓库、门店实体：资产、产品交易：订单、付款事件：告警、质检工作项：工单、案件决策：排产、补货建议

主键与标题属性

对象类型：Asset
主键属性：assetId = A-1001      // 机器稳定唯一识别
标题属性：assetName = 一号循环泵 // 人类快速识别

主键必须唯一、非空、确定且长期稳定。随机行号或同步后变化的标识会让编辑和关系失效。

关系是双向语义

Asset资产
locatedAt / assets
Location地点
belongsTo / assets
Department部门

Palantir 的 Link Type 本身是双向的，两侧分别拥有显示名称和 API 名称。数据库外键的存储方向不应限制业务遍历方向。

基数与关系对象化

模式使用场景例子
一对一两边最多一个员工 ↔ 当前工位
一对多 / 多对一一侧可关联多个部门 ↔ 员工
多对多双方都可多个供应商 ↔ 产品
关系对象化关系拥有日期、角色、金额或生命周期员工 → 项目任职 → 项目

04组、共享属性、接口与继承

能力解决的问题不要误解为
对象类型组分类、发现、过滤和图谱聚合不会自动产生共同属性
共享属性集中复用属性名称、类型和说明共享的是元数据，不是实例值
接口让多种具体对象遵守同一结构和能力契约接口不能直接实例化
子类 / 继承表达“所有 A 都是 B”的语义不适合为了代码复用而无限加深
接口例子：WorkItemMaintenanceOrder、ServiceTicket 和 ApprovalTask 都实现 status、assignee、dueDate。应用和智能体便能对“所有工作项”进行通用查询和动作。

实务选择：仅导航使用组；统一一个字段使用共享属性；统一结构与能力使用接口；真正需要语义推理时才使用子类关系。

05Action：从“名词”走向“业务变化”

对象、属性和关系描述现在的世界；Action 描述谁可以在什么条件下，以什么参数把世界改变成什么样。

参数asset、nextStatus、reason
提交条件身份、对象状态、参数
规则创建/修改对象与关系
副作用通知、Webhook、调度
审计调用者、输入、结果
action: changeAssetStatus
parameters:
  asset: Asset
  nextStatus: AssetStatus
  reason: string
rules:
  - set asset.status = nextStatus
  - set asset.lastUpdatedAt = currentTime
submissionCriteria:
  - currentUser in AssetAdministrators
  - asset.status != 已报废
对智能体尤其重要让 LLM 选择窄而明确的 Action，不给它任意 SQL 或数据库写权限。Action 统一执行权限、业务条件、影响预览和审计。

06数据如何进入本体

本体不是给数据库表换中文名。对象类型必须和真实数据建立可追踪、可验证的绑定。

dataset.asset_master.asset_code  → Asset.assetId（主键）
dataset.asset_master.asset_name  → Asset.assetName（标题）
dataset.asset_master.dept_code   → Asset.belongsToDepartment
dataset.asset_state.state_code   → Asset.status
数据源数据集、视图、API、事件流及其负责人和刷新频率。
字段映射类型转换、枚举转换、空值、默认值、主键和标题键。
关系来源外键、关联表或拥有元数据的 backing object。
实体解析多来源记录的匹配、合并、冲突策略与人工复核。
质量与索引唯一性、完整性、新鲜度、覆盖率和索引错误。
血缘与安全知道数据从哪里来、谁能看、谁能修改。

典型建模操作

选择本体上下文

在当前 Space / Ontology 中搜索已有资源，优先复用。

创建对象并映射数据

选择数据源、属性、主键、标题键和元数据。

创建关系与 Action

定义双向语义、基数、参数、规则和提交条件。

在分支预览

检查数据、索引、权限、接口实现和下游影响。

Proposal 审查与合并

查看 Diff、评审任务、批准并合入 main。

多个本体的边界不同 Ontology 之间不能直接建立 Link Type。跨域对象若需要正式语义关系，通常应进入共同或共享 Ontology；业务域内部可用对象类型组划分。

09治理：本体是公共契约

生命周期试验、启用、核心推荐、弃用、示例。
模型权限谁能查看、编辑和管理资源定义。
实例权限谁能看到哪些对象和属性、运行哪些动作。
Branch隔离建模变更和预览数据。
Proposal像 Pull Request 一样展示 Diff、任务和评审。
影响分析变更前查找应用、SDK、Agent、映射和 Action 消费者。

发布前检查

  • 每个对象恰好一个稳定主键
  • 标题属性真实存在
  • API 名称唯一且稳定
  • 关系端点和基数正确
  • 接口实现满足契约
  • 共享属性类型一致
  • Action 参数与规则匹配
  • 提交条件有清晰失败信息
  • 数据样本、索引和权限预览通过
  • 没有破坏下游消费者

10可靠的手工建模方法

从问题和动作开始

先写 5～10 个必须回答的问题和 3～5 个必须完成的动作。

建立业务词汇表

给出定义、反例、同义词、负责人和来源。

识别对象与身份

寻找有稳定身份和独立生命周期的实体、事件与工作项。

设计最小属性集

明确类型、枚举、敏感级别、来源与说明。

只建立有意义的关系

每条关系都应能回答一个自然业务问题。

复用与抽象

使用组、共享属性和接口，但避免过早抽象。

设计受控 Action

明确参数、规则、条件、影响和审计。

绑定数据与真实样本

检查唯一性、空值、枚举、覆盖率和新鲜度。

小范围发布

让一个真实应用或智能体消费，再根据反馈演进。

11本体如何驱动智能体

本体把智能体从“猜表名、拼 SQL 的聊天模型”，升级为“理解业务对象、沿关系查询、通过受控动作办事的数字员工”。

角色 1消费本体读取对象、属性、关系、查询和 Action 契约。
角色 2辅助建模从文件、Schema 和样例中提出有证据的候选变更。
角色 3操作本体在权限、条件、确认和审计约束下调用 Action。
用户意图“为 A-1001 创建高优先级维修工单”
→
Agent 规划查询资产、已有工单、可用动作和权限
→
Ontology 工具queryObjects / traverseLinks / createMaintenanceOrder
读写分离读路径可以搜索、过滤、聚合和遍历；写路径只调用已发布 Action，执行权限与提交条件，高影响动作要求人工确认，并记录审计。

本体与 RAG

RAG / 向量检索本体
找到相关非结构化文本和证据表达结构化业务对象、关系和动作
相似度不等于正式业务关系关系具有类型、端点和基数
回答“依据在哪里”回答“对象是什么、怎么连接、能做什么”

组合方式：RAG 找证据，本体提供结构，Query / Function 计算，Action 执行改变。

Palantir AIP / Agents

Foundry Agent 通常绑定选定 Ontology，通过 OSDK、Ontology MCP 和 Palantir MCP 获得有范围的对象、查询和 Action 工具。发布后 Agent 拥有 Ontology binding 与 API 名称，可从 Workshop、Automate、SDK 或 Ontology Action 触发。

Evidence Set文件、表、API、术语

Proposal证据、置信度、Diff

AI 适合完成

  • 发现领域名词、事件和动作
  • 推断候选对象与属性
  • 生成说明、同义词和命名建议
  • 发现重复概念和接口机会
  • 提出关系、基数和枚举候选
  • 建议字段映射
  • 解释 Diff 和影响
  • 生成校验规则与测试数据

必须由人或确定性政策决定

  • 最终主键和主数据身份
  • 高影响实体合并
  • 敏感数据权限
  • Action 执行授权
  • 删除和破坏性迁移
  • 没有证据的业务规则
  • 正式版本发布
AI 输出是 Proposal，不是事实每个候选资源都应保存来源、原文证据、推断理由、置信度、与现有资源的冲突以及审查状态。

13智能体安全护栏

最小权限只暴露完成任务需要的对象、属性、查询和 Action。
结构化工具明确类型、枚举、说明、失败行为和幂等性。
高影响确认展示目标对象、参数、预计变化、下游影响和可撤销性。
内容不可信文档、网页和属性值不能覆盖系统政策或授予权限。
完整审计记录模型、提示词、对象、工具参数、确认和执行结果。
持续 Evals评估查询路径、工具选择、参数、拒绝和确认策略。
危险工具：execute_sql(sql)

推荐工具：retire_asset(
  assetId: string,
  reason: string,
  effectiveDate: date
)
→ 权限检查 → 业务条件 → 影响预览 → 人工确认 → 执行 → 审计

14八个常见误区

本体就是知识图谱图谱强调实体关系数据；本体强调类型、约束、契约和治理，运营本体还包含动作。
一张表对应一个对象表是存储结构，对象是业务概念；两者不是一一对应。
能 Join 就建关系关系必须回答业务问题，否则只会增加噪声。
节点越多越专业质量取决于是否支持稳定的问题和动作。
API 名称可以随便改它是应用、SDK、自动化和 Agent 的公共契约。
AI 可自动发布本体AI 适合生成候选，身份、权限和高影响动作必须治理。
有本体就不需数据治理重复主键、错误枚举和过期数据仍需工程机制。
Agent 可以直接写库企业写路径必须收敛到受控 Action。

15本体平台的推荐分期

阶段目标核心范围
一期
可信手工内核		本体可建、可查、可验证、可版本化六类核心资源、结构化映射、实例预览、图谱、Diff、版本和审计
二期
AI 建模		从证据生成可审查的候选变更Evidence Set、抽取对齐、Proposal、引用、置信度和建模 Eval
三期
Agent Runtime		让 Agent 安全查询并执行企业动作Query、Function、Action、权限、确认、审计、自动化和在线评估
产品原则先把手工建模和治理内核做正确，再让 AI 提建议，最后让 Agent 执行动作。AI 能力不能替代元模型、权限和版本基础。
